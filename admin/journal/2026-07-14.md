# Research Journal — 2026-07-14

## Session focus

Pipeline observability: adding execution time tracking to labelling and training pipelines.

## Context

- Current pipeline tracks record counts per stage (`stage_counts`) but has no timing instrumentation
- Training pipeline already tracks per-model `training_duration_seconds` but no overall pipeline time
- Experiment log (`experiment_log.jsonl`) has no duration fields
- This is low-effort, high-value work for the final report — provides concrete performance data

## Decision: Implement pipeline timing instrumentation

### Rationale

1. **Report content** — a table of stage durations gives concrete evidence of system understanding and identifies the computational bottleneck (likely sentiment computation on 80k+ records)
2. **Reproducibility** — extends the R7 narrative beyond deterministic outputs to consistent execution characteristics
3. **Experiment comparison** — timing in the experiment log enables detecting performance regressions when parameters change (e.g., switching sentiment models)
4. **Near-zero cost** — `time.perf_counter()` calls, ~20-30 lines of code total, no new dependencies, no architectural changes

### Summary of changes planned

| File | Change |
|------|--------|
| `src/surge_pipeline/pipeline.py` | Wrap each stage in `perf_counter()`, add `stage_durations` + `total_duration_seconds` to results dict and JSON output |
| `src/run_labeling.py` | Print timing table, include duration in experiment log |
| `src/run_training.py` | Wrap full pipeline in timer, include duration in experiment log |

## Experiment C1: r/wallstreetbets 2021 dataset

### Objective

Test whether a fundamentally denser dataset resolves the data sparsity problem (89% exclusion, only 7 test surges) identified in the model improvement plan.

### Dataset

- Source: r/wallstreetbets 2021 (Kaggle), 1,293,981 raw records
- Period: 2021-01-01 to 2021-12-31
- No pre-extracted tickers (extracted from title/selftext by loader)
- SHA256: `3ce3697d...`

### Config

- `min_window_count=1`, `threshold_tau=1.5`, `sentiment_model=vader`
- `surge_method=forward_growth`, `temporal_split_ratio=0.8`, `random_seed=42`

### Labelling Results

| Metric | r/pennystocks (baseline) | r/wallstreetbets (C1) |
|--------|--------------------------|------------------------|
| Raw records | 80,212 | 1,293,981 |
| After load (exploded by ticker) | — | 577,872 |
| Exclusion rate | 89% | 20.9% |
| Usable records | ~8,577 | 457,072 |
| Surge count (all) | ~189 | 6,602 |
| Surge rate | 2.2% | 1.44% |
| Test surges | 7 | 668 |
| Imbalance ratio (test) | ~44:1 | 102:1 |
| Pipeline duration | — | 900.6s (sentiment: 870s) |

**Key finding:** Data sparsity solved — 668 test surges provides statistically meaningful evaluation. However, surge rate dropped to 1.44%, worsening class imbalance.

### Evaluation Results

| Model | AUC | Precision | Recall | F1 |
|-------|-----|-----------|--------|-----|
| Logistic Regression | 0.707 | 0.013 | 0.80 | 0.026 |
| Random Forest | 0.876 | 0.040 | 0.79 | 0.076 |
| XGBoost | **0.888** | 0.0 | 0.0 | 0.0 |

### Interpretation
**XGBoost is now the best model** — with 388K training samples and 11 features, XGB's sequential boosting and regularisation excels. On sparse pennystocks data RF won because it's more robust to noise; on dense data XGB's higher capacity pays off.

**AUC vs precision/recall disconnect** — XGB achieves the highest AUC (0.888) but predicts almost no surges at the default 0.5 threshold (precision=0, recall=0). This means the model ranks surges correctly (high AUC) but needs a lower decision threshold to produce actual positive predictions. The default threshold is inappropriate for a 1.4% base rate.

RF has the best operational metrics — 79.2% recall at 4% precision with 0.876 AUC. If you adjust the classification threshold, RF would likely produce a strong precision-recall tradeoff.

McNemar's tests are all significant — all model pairs are statistically different (p≈0), which is meaningful with 68K test samples.

The data was the bottleneck, not the algorithm. Going from 24K → 457K records with better ticker density produced a +13.5% AUC improvement — far more than any feature engineering experiment achieved.

### Key takeaway
The improvement plan was correct: Track C (denser dataset) was the highest-impact move. Feature engineering (B2: +1.4%) was useful but small. Data quality/quantity (C1: +13.5%) was transformative.

### Diagnosis

**Positive:**
- AUC lifted significantly: XGBoost 0.888, RF 0.876 (vs. 0.77 on pennystocks). Signal is genuinely stronger.
- 668 test surges → AUC numbers are trustworthy (not the case with 7 surges before).

**Negative — precision/recall collapse:**
- XGBoost predicts everything as no-surge (exploits 102:1 imbalance, never predicts positive).
- LR labels ~58% of test set as surge to achieve 80% recall → 1.3% precision (unusable).
- RF best balance but 4% precision still impractical.

**Root cause:** Extreme imbalance (1.44% surge rate at τ=1.5). Models rank well (high AUC = good discrimination) but can't find a useful decision boundary at the default 0.5 threshold.

### Next steps

1. **Lower τ to 1.0** — push surge rate toward 3–5%, reduce imbalance ratio
2. **Add class weighting** — `class_weight='balanced'` for LR/RF, `scale_pos_weight≈70` for XGBoost
3. **Tune decision threshold** — AUC 0.888 proves XGBoost can rank; lower the classification cutoff (e.g., 0.02) to recover recall without collapsing precision

The dataset switch validated: the ranking signal is strong. The remaining problem is calibration/threshold, not feature quality.
