## Architecture review — areas for improvement identified

### Context

Performed a full review of the project architecture to assess code organisation, data flow, and engineering quality. The system is well-structured overall (clean separation of concerns, reproducibility-first design, no temporal leakage, systematic experimentation). Seven improvement areas were identified:

### Areas for improvement

1. **No package installation (ADDRESSED)** — No `setup.py` or `pyproject.toml` existed. CLI scripts used `sys.path.insert(0, ...)` hacks to make `surge_pipeline` importable. Added `pyproject.toml` (PEP 621) to enable `pip install -e .` for proper editable installs.

2. **Test coverage is narrow** — 6 test files for 15 modules. Missing coverage for: `loader.py` (ticker extraction edge cases), `windowing.py` (critical algorithmic code), `pipeline.py` (integration tests), `config.py` (serialisation roundtrip tests).

3. **Duplicate logic between pipelines** — `run_threshold_sweep` in `pipeline.py` re-runs stages 1–3 identically to `run_pipeline`. A shared "run up to stage N" abstraction would reduce this duplication.

4. **Hardcoded constants** — `_WINDOW_SECONDS = 24 * 60 * 60` appears in both `windowing.py` and `sentiment.py`. Could be a config parameter or a shared constant to avoid drift.

5. **No type checking / linting CI** — Code uses type hints throughout (good) but no `mypy` or `ruff` in requirements or CI. Adding static analysis would catch type drift and style issues early.

6. **Scripts are Bash-only** — `m1.sh`, `m2.sh` etc. won't run on Windows natively. Cross-platform Python-based runner scripts would improve portability (relevant since development happens on Windows).

7. **Output directory accumulates unboundedly** — Timestamped output files are never cleaned up. A retention policy or archival script would help manage disk usage over many experiment runs.

### Priority assessment

- Items 1 (packaging) is now resolved.
- Items 2–5 are engineering hygiene — valuable for long-term maintenance but not blockers for the dissertation.
- Items 6–7 are convenience improvements with no impact on results or report.

## Added `pyproject.toml`

### Change

Created `pyproject.toml` at project root with:
- Build system: setuptools
- All runtime dependencies (from `requirements.txt`)
- Dev dependencies (pytest) as optional extra
- Console script entry points for all 5 CLI tools (`surge-label`, `surge-train`, `surge-cross-val`, `surge-figures`, `surge-examples`)
- pytest configuration (testpaths, pythonpath)
- Package discovery pointing to `src/`

### Rationale

`pyproject.toml` is the modern Python packaging standard (PEP 621/517). Using it instead of `setup.py` because:
- `setup.py` is effectively legacy
- Single file for metadata, dependencies, build config, and tool settings
- Enables `pip install -e .` which eliminates the `sys.path` hacks in CLI scripts
- Makes the project installable for any downstream consumer

### No new design decisions

This is a packaging/tooling change. No pipeline logic, features, or methodology affected.
