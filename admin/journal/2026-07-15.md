# Research Journal — 2026-07-15

## Session focus

CLI logging implementation: built-in `--log-file` flag for capturing full run output to file.

## Context

- Pipeline runs produce long terminal output (config, stage summaries, metrics, timing)
- Scrolling back through terminal history is unreliable for tracing past runs
- Shell redirection (`2>&1 > file.log`) works but is easy to forget and platform-specific
- Need a built-in, cross-platform solution that preserves console display while capturing to file

## Decision: Tee-style `--log-file` flag on both CLI runners

### Rationale

1. **Traceability** — full capture of stdout, stderr, and Python logging output for each run
2. **Zero friction** — single flag (`--log-file auto`) auto-names with timestamp + pipeline name
3. **Console preserved** — tee approach means you still see everything live; log file is a bonus
4. **Links to experiment log** — auto-generated filenames use the same timestamp pattern as `experiment_log.jsonl` entries, making cross-referencing easy
5. **No new dependencies** — pure stdlib implementation (`sys.stdout` replacement + `logging.FileHandler`)

### Implementation

| File | Change |
|------|--------|
| `src/surge_pipeline/cli_logging.py` | New module: `TeeStream` class, `resolve_log_path()`, `tee_output()` context manager |
| `src/run_labeling.py` | Added `--log-file` argument, imported `cli_logging`, wrapped `main()` body in `tee_output()` |
| `src/run_training.py` | Added `--log-file` argument, imported `cli_logging`, wrapped `main()` body in `tee_output()` |
| `README.md` | Documented flag usage, added CLI Log Files section, updated project structure |

### Design details

- `TeeStream` wraps the original stdout/stderr and a log file handle; every `write()` goes to both
- `resolve_log_path("auto", pipeline="labelling")` → `output/logs/2026-07-15_10-30-45_labelling.log`
- `resolve_log_path("myrun.log")` → `output/logs/myrun.log`
- `resolve_log_path(None)` → `None` (no-op, backward compatible)
- Context manager also attaches a `logging.FileHandler` to the root logger so that `logger.info()` calls are captured even if they bypass `print()`
- Log file header includes command line, timestamp, and Python version

### Usage

```bash
# Auto-timestamped log
python run_labeling.py --file-path ../input/raw/r_pennystocks_submissions_reddit.csv --verbose --log-file auto
```

## Cross-dataset validation results (08:40 run)

### Experiment

Evaluated WSB-trained models on the r/pennystocks labelled dataset (test partition only).

- **Eval dataset:** `output/processed/labelled_dataset.csv` (test partition)
- **Eval set size:** 3,278 samples (31 surges, 3,247 non-surges — 0.95% surge rate)
- **Models:** logistic_regression, random_forest, xgboost (all trained on r/wallstreetbets)

### Results

| Model | AUC | Precision | Recall | F1 | Notes |
|-------|-----|-----------|--------|-----|-------|
| XGBoost | 0.694 | 0.000 | 0.000 | 0.000 | Predicts all-negative; threshold too conservative |
| Random Forest | 0.656 | 0.016 | 0.613 | 0.031 | Finds surges but massive false positive rate |
| Logistic Regression | 0.652 | 0.013 | 0.742 | 0.025 | Most liberal — high recall, near-zero precision |

### Interpretation

1. **Ranking generalises (partially):** All models beat random (AUC 0.65–0.69), confirming that learned features capture some transferable surge signal across communities.
2. **Calibration does not transfer:** The decision threshold calibrated on WSB fails catastrophically on pennystocks. XGBoost predicts every record as non-surge; logistic regression flags ~54% of all records as surges.
3. **Class imbalance dominates:** With only 0.95% positive base rate, the default 0.5 threshold is inappropriate. XGBoost's 99% accuracy is a trivial majority-class predictor.
4. **XGBoost is the best generaliser by AUC** — its probability scores rank surges above non-surges most reliably, despite the threshold issue.

### Implications

- AUC should be the primary metric for cross-community transfer evaluation (threshold-independent).
- Deployment to a new community requires threshold recalibration, even with a small local calibration set.
- Consider retraining with balanced class weights or adjusting threshold to ~0.1–0.2 (matching base rate) for practical cross-community use.
- These results support the thesis that surge dynamics are partially community-agnostic but calibration is community-specific.

## P1 Implementation: Classification Threshold Tuning

### Problem

All models used sklearn's default 0.5 decision threshold. With a 0.95–1.44% surge base rate, this is far too conservative — XGBoost achieves AUC=0.888 (WSB) / 0.737 (pennystocks) but predicts zero surges. The models rank correctly but the operating point is unusable.

### Solution: Validation-fold threshold selection (Option A)

Select the optimal classification threshold on the **last temporal CV validation fold**, avoiding test-set leakage. The threshold is persisted in the saved model `.joblib` file for downstream use.

### Implementation

| File | Change |
|------|--------|
| `src/surge_pipeline/evaluation.py` | Added `ThresholdResult` dataclass and `find_optimal_threshold()` — sweeps thresholds 0.01–0.99, supports `max_f1` and `precision_floor` strategies |
| `src/surge_pipeline/training.py` | Added `val_y_true`/`val_y_prob` fields to `TrainedModel`; `_train_single_model()` now generates predictions on last CV fold after final retrain; `train_models()` computes optimal threshold and stores it in `.joblib`; added `predict_with_threshold()` utility |
| `src/run_training.py` | Added section 7b: prints comparison table (default vs tuned), saves `{prefix}_threshold_tuning.json` |
| `src/run_cross_validation.py` | `evaluate_cross_dataset()` reads `optimal_threshold` from model dict, reports metrics at both 0.5 and tuned threshold |

### Design decisions

- **Threshold selection on last CV fold** — the final model is trained on all training data, then evaluated on the last fold (which it has seen during final fitting). This is a slight compromise vs. a held-out validation split, but avoids further reducing training data. The fold provides temporal ordering consistent with the test set.
- **Max F1 strategy** — chosen over precision floor because F1 balances both precision and recall without requiring a subjective floor parameter.
- **Threshold stored in .joblib** — enables any downstream script to use it without recomputing. Backward-compatible: missing key defaults to 0.5.

### Results (r/pennystocks, 11:18 run)

**Default threshold (0.5):**

| Model | AUC | Precision | Recall | F1 |
|-------|-----|-----------|--------|-----|
| Logistic Regression | 0.680 | 0.013 | 0.645 | 0.025 |
| Random Forest | 0.744 | 0.125 | 0.129 | 0.127 |
| XGBoost | 0.737 | 0.000 | 0.000 | 0.000 |

**Tuned threshold (selected on validation fold):**

| Model | Threshold | Precision | Recall | F1 | Δ F1 |
|-------|-----------|-----------|--------|-----|------|
| Logistic Regression | 0.67 | 0.085 | 0.194 | 0.118 | +0.093 |
| Random Forest | 0.56 | 0.136 | 0.097 | 0.113 | −0.014 |
| **XGBoost** | **0.18** | **0.158** | **0.194** | **0.174** | **+0.174** |

### Interpretation

1. **XGBoost unlocked:** Goes from completely dead (F1=0) to the best operational model (F1=0.174). Threshold dropped from 0.5 → 0.18, allowing it to predict positive for high-confidence cases.
2. **LR improved by raising threshold:** From 0.50 → 0.67. LR was over-predicting (1,546 false positives); raising the cutoff reduced FP to 65, improving precision from 1.3% → 8.5%.
3. **RF nearly unchanged:** Threshold moved only 0.50 → 0.56 — the model was already operating near its optimum.
4. **Absolute numbers still modest** — 31 test surges is too few for high-confidence metrics. The real payoff will come from retraining on WSB (668 test surges, AUC=0.888).

### Validation fold metrics (for reference)

| Model | Val Threshold | Val Precision | Val Recall | Val F1 |
|-------|---------------|---------------|------------|--------|
| Logistic Regression | 0.67 | 0.198 | 0.393 | 0.263 |
| Random Forest | 0.56 | 0.743 | 0.964 | 0.839 |
| XGBoost | 0.18 | 0.351 | 0.393 | 0.371 |

Note: RF's validation metrics are dramatically better than test — this is expected because the validation fold comes from the same temporal window as training, while the test set is a distinct future period with only 31 surges.

| XGBoost | 0.13 | 0.141 | 0.241 | 0.178 | +0.178 |

### Interpretation (WSB run)

1. **Random Forest is the best operational model** — F1=0.192 (highest), 18.2% precision, 20.4% recall. Threshold 0.85 means only high-confidence predictions pass.
2. **XGBoost unlocked from zero** — F1 jumps 0.000 → 0.178 (largest absolute gain). Threshold dropped to 0.13; the model needed an extremely low cutoff to produce positive predictions. 161 true positives found (24.1% of surges).
3. **LR tripled its F1** — threshold went *up* to 0.81 (was massively over-predicting at 0.5: 40K false positives reduced to 3K).
4. **Precision ceiling ~18%** — even with tuning, precision tops out around 18%. Reflects the fundamental 0.97% base rate (668/68,923). Exceeding ~20% precision likely requires class rebalancing (P6), richer features, or τ=1.0 (P5).
5. **All thresholds are extreme** — 0.13 (XGB), 0.81/0.85 (LR/RF). Models' probability outputs are not well-calibrated for the actual base rate. Platt scaling or isotonic calibration could be a future improvement.

### Design consistency check

Threshold tuning does **not** violate the existing design:
- **Surge definition (DEC-013):** τ is untouched — the classification threshold is a separate concept from the labelling threshold.
- **Evaluation goals (DEC-007):** AUC-ROC (primary metric) is threshold-independent. F1 at tuned threshold is supplementary.
- **Class imbalance handling (DEC-021):** Explicitly anticipated: *"Threshold adjustment (post-hoc) — complementary, not alternative: the threshold sensitivity analysis already sweeps classification thresholds."*
- **Temporal integrity (DEC-017/018):** Threshold selected on last CV validation fold (temporally after training data). No leakage.
