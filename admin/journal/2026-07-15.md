# Research Journal — 2026-07-15

## Session focus

CLI logging implementation: built-in `--log-file` flag for capturing full run output to file.

## Context

- Pipeline runs produce long terminal output (config, stage summaries, metrics, timing)
- Scrolling back through terminal history is unreliable for tracing past runs
- Shell redirection (`2>&1 > file.log`) works but is easy to forget and platform-specific
- Need a built-in, cross-platform solution that preserves console display while capturing to file

## Decision: Tee-style `--log-file` flag on both CLI runners

### Rationale

1. **Traceability** — full capture of stdout, stderr, and Python logging output for each run
2. **Zero friction** — single flag (`--log-file auto`) auto-names with timestamp + pipeline name
3. **Console preserved** — tee approach means you still see everything live; log file is a bonus
4. **Links to experiment log** — auto-generated filenames use the same timestamp pattern as `experiment_log.jsonl` entries, making cross-referencing easy
5. **No new dependencies** — pure stdlib implementation (`sys.stdout` replacement + `logging.FileHandler`)

### Implementation

| File | Change |
|------|--------|
| `src/surge_pipeline/cli_logging.py` | New module: `TeeStream` class, `resolve_log_path()`, `tee_output()` context manager |
| `src/run_labeling.py` | Added `--log-file` argument, imported `cli_logging`, wrapped `main()` body in `tee_output()` |
| `src/run_training.py` | Added `--log-file` argument, imported `cli_logging`, wrapped `main()` body in `tee_output()` |
| `README.md` | Documented flag usage, added CLI Log Files section, updated project structure |

### Design details

- `TeeStream` wraps the original stdout/stderr and a log file handle; every `write()` goes to both
- `resolve_log_path("auto", pipeline="labelling")` → `output/logs/2026-07-15_10-30-45_labelling.log`
- `resolve_log_path("myrun.log")` → `output/logs/myrun.log`
- `resolve_log_path(None)` → `None` (no-op, backward compatible)
- Context manager also attaches a `logging.FileHandler` to the root logger so that `logger.info()` calls are captured even if they bypass `print()`
- Log file header includes command line, timestamp, and Python version

### Usage

```bash
# Auto-timestamped log
python run_labeling.py --file-path ../input/raw/r_pennystocks_submissions_reddit.csv --verbose --log-file auto

# Specific filename
python run_training.py --data-path ../output/processed/labelled_dataset.csv --log-file experiment_c2.log

# No logging (default, same as before)
python run_labeling.py --file-path ../input/raw/r_pennystocks_submissions_reddit.csv
```

## Cross-dataset validation results (08:40 run)

### Experiment

Evaluated WSB-trained models on the r/pennystocks labelled dataset (test partition only).

- **Eval dataset:** `output/processed/labelled_dataset.csv` (test partition)
- **Eval set size:** 3,278 samples (31 surges, 3,247 non-surges — 0.95% surge rate)
- **Models:** logistic_regression, random_forest, xgboost (all trained on r/wallstreetbets)

### Results

| Model | AUC | Precision | Recall | F1 | Notes |
|-------|-----|-----------|--------|-----|-------|
| XGBoost | 0.694 | 0.000 | 0.000 | 0.000 | Predicts all-negative; threshold too conservative |
| Random Forest | 0.656 | 0.016 | 0.613 | 0.031 | Finds surges but massive false positive rate |
| Logistic Regression | 0.652 | 0.013 | 0.742 | 0.025 | Most liberal — high recall, near-zero precision |

### Interpretation

1. **Ranking generalises (partially):** All models beat random (AUC 0.65–0.69), confirming that learned features capture some transferable surge signal across communities.
2. **Calibration does not transfer:** The decision threshold calibrated on WSB fails catastrophically on pennystocks. XGBoost predicts every record as non-surge; logistic regression flags ~54% of all records as surges.
3. **Class imbalance dominates:** With only 0.95% positive base rate, the default 0.5 threshold is inappropriate. XGBoost's 99% accuracy is a trivial majority-class predictor.
4. **XGBoost is the best generaliser by AUC** — its probability scores rank surges above non-surges most reliably, despite the threshold issue.

### Implications

- AUC should be the primary metric for cross-community transfer evaluation (threshold-independent).
- Deployment to a new community requires threshold recalibration, even with a small local calibration set.
- Consider retraining with balanced class weights or adjusting threshold to ~0.1–0.2 (matching base rate) for practical cross-community use.
- These results support the thesis that surge dynamics are partially community-agnostic but calibration is community-specific.
