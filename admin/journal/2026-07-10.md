# Research Journal — 2026-07-10

## Session focus

Fix the pandas datetime resolution portability bug identified in the July 9 investigation.

## Bug Summary

**Problem:** The pipeline produced different results on different environments despite identical code, config, and input data. One environment excluded 89% of records (correct), the other excluded only 29% (broken windowing).

**Root cause:** Pandas 2.x can store datetimes as `datetime64[us]` (microseconds) instead of `datetime64[ns]` (nanoseconds) depending on version/backend. The pattern `.astype("int64") // 10**9` assumes nanosecond resolution:

- `datetime64[ns]` → `.astype("int64")` = nanoseconds → `// 10**9` = correct seconds
- `datetime64[us]` → `.astype("int64")` = microseconds → `// 10**9` = **seconds ÷ 1000** (wrong!)

This made all timestamps collapse to near-zero values, causing the 24h window (86,400 seconds) to encompass the entire dataset, inflating forward counts and reducing exclusion.

## Fix Applied

### New module: `src/surge_pipeline/timestamps.py`

Created a shared utility with a resolution-independent conversion:

```python
def to_epoch_seconds(series: pd.Series) -> np.ndarray:
    epoch = pd.Timestamp("1970-01-01", tz="UTC")
    return ((series - epoch).dt.total_seconds()).values.astype(np.int64)
```

This uses `dt.total_seconds()` which works correctly regardless of internal datetime resolution (ns, us, ms, s).

## Sentiment Stage Performance Optimisation

### Problem

Stage 3 (sentiment computation) was taking excessively long with VADER. The pipeline runs VADER on all ~80,000 records, but 89% (~71,600) are excluded by the windowing stage and end up with `sentiment_change = 0` regardless. Computing polarity for records that won't influence training is pure waste.

### Root Cause

Two nested performance problems in `sentiment.py`:

1. **Step 1 (polarity):** Row-by-row Python loop calling `polarity_fn()` on all 80k records. At ~0.5–1ms per VADER call, this takes 40–80 seconds.
2. **Step 2 (forward window):** Grouped iteration over all 80k records to compute `mean_future_sentiment`, even though excluded records get overwritten to `sentiment_change = 0` at the end.

### Fix Applied

Modified `compute_sentiment()` to skip excluded records in both steps:

- **Step 1:** Only iterate over `included_indices = np.where(~excluded)[0]` (~8,500 records). Excluded records retain `polarity = 0.0`.
- **Step 2:** Set `mean_future[excluded] = polarities[excluded]` upfront (guaranteeing `sentiment_change = 0`). Only run the per-ticker groupby loop on `included_df`.
- **Index mapping:** Added `index_to_pos` lookup (DataFrame label → positional index) so the filtered groupby correctly addresses the full-length arrays.

### Expected Speedup

With 89% exclusion: ~9x faster on both Step 1 (8,500 vs 80,000 VADER calls) and Step 2 (8,500 vs 80,000 forward-window iterations).
