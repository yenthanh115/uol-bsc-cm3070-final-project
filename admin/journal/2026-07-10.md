# Research Journal — 2026-07-10

## Session focus

Fix the pandas datetime resolution portability bug identified in the July 9 investigation.

## Bug Summary

**Problem:** The pipeline produced different results on different environments despite identical code, config, and input data. One environment excluded 89% of records (correct), the other excluded only 29% (broken windowing).

**Root cause:** Pandas 2.x can store datetimes as `datetime64[us]` (microseconds) instead of `datetime64[ns]` (nanoseconds) depending on version/backend. The pattern `.astype("int64") // 10**9` assumes nanosecond resolution:

- `datetime64[ns]` → `.astype("int64")` = nanoseconds → `// 10**9` = correct seconds
- `datetime64[us]` → `.astype("int64")` = microseconds → `// 10**9` = **seconds ÷ 1000** (wrong!)

This made all timestamps collapse to near-zero values, causing the 24h window (86,400 seconds) to encompass the entire dataset, inflating forward counts and reducing exclusion.

## Fix Applied

### New module: `src/surge_pipeline/timestamps.py`

Created a shared utility with a resolution-independent conversion:

```python
def to_epoch_seconds(series: pd.Series) -> np.ndarray:
    epoch = pd.Timestamp("1970-01-01", tz="UTC")
    return ((series - epoch).dt.total_seconds()).values.astype(np.int64)
```

This uses `dt.total_seconds()` which works correctly regardless of internal datetime resolution (ns, us, ms, s).
