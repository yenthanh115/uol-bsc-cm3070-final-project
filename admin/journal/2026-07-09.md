# Research Journal — 2026-07-09

## Session focus

Diagnosing the large discrepancy between the July 8 and July 9 pipeline runs. Full pipeline re-run after code fix, followed by comparative analysis of outputs.

## Observation: Two runs produce radically different results

Comparing `2026-07-08_pipeline_summary.json` and `2026-07-09_pipeline_summary.json` reveals a massive divergence across every metric despite identical config parameters (τ=1.5, w₂=0.5, min_window_count=3, seed=42, sentiment_model=vader).

## Root cause: `split_timestamp` unit mismatch

| | July 8 run | July 9 run |
|---|---|---|
| `split_timestamp` | 1,628,120,809.2 (Unix seconds — Aug 4, 2021) | 1,628,120.6 (not a standard unit) |

The July 8 split timestamp is a valid Unix epoch (seconds). The July 9 value is ~1000× smaller, suggesting a unit conversion change in how the temporal split point is computed or how timestamps in the dataset are being interpreted (seconds vs milliseconds, or a division applied somewhere).

## Cascade effect on all downstream metrics

### 1. Exclusion rate: 89% → 29%

| | July 8 | July 9 |
|---|---|---|
| Excluded records | 71,635 | 23,598 |
| Exclusion rate | **89.3%** | **29.4%** |
| Records retained | 8,577 | 56,614 |

The July 8 run excludes nearly 90% of records — far exceeding the "moderate exclusion" anticipated in DEC-011. This suggests the windowing logic was treating most per-ticker 24h windows as having fewer than 3 records (the `min_window_count` threshold), likely because a timestamp unit mismatch made the 24h window effectively much smaller than intended.

The July 9 run retains ~57K of 80K records (29% exclusion), which aligns much better with expectations for the pennystocks dataset.

### 2. Training/test size

| | July 8 | July 9 |
|---|---|---|
| Train size | 8,058 | 49,495 |
| Test size | 519 | 7,119 |
| Test surges | **7** | **80** |

With only 7 positive examples in the July 8 test set, all evaluation metrics are dominated by noise. A single misranked example swings AUC by ~0.07. The July 9 run with 80 test surges provides statistically meaningful estimates.

### 3. Normalisation parameters

| | July 8 | July 9 |
|---|---|---|
| μ_volume | 1.44 | 4.24 |
| σ_volume | 3.31 | 14.48 |
| μ_sentiment | 0.360 | 0.374 |
| σ_sentiment | 0.279 | 0.282 |

Volume parameters diverge significantly (the July 8 run sees compressed growth ratios because fewer records pass the filter). Sentiment parameters are stable — expected since sentiment is text-derived and not affected by windowing logic.

### 4. Model performance

| Model | July 8 AUC | July 9 AUC |
|-------|-----------|-----------|
| LR | 0.646 (minimum tier) | 0.854 (stretch tier) |
| RF | 0.770 (target tier) | 0.975 (stretch tier) |
| XGBoost | 0.707 (target tier) | 0.981 (stretch tier) |

### 5. Best single-feature baseline flipped

| | July 8 | July 9 |
|---|---|---|
| Best single feature | word_count (AUC=0.809) | sentiment_score (AUC=0.968) |
| Sentiment single-feature AUC | 0.465 (below random) | 0.968 (dominant) |

This is the most striking flip: sentiment goes from useless to dominant between runs. This is directly caused by the sample size — with 7 test surges (July 8), the single-feature AUC estimates are essentially random; with 80 test surges (July 9), they stabilise.

## Assessment: Which run is valid?

**July 9 is the operationally correct run** based on:
- Exclusion rate (29%) aligns with EDA expectations
- Test set size (7,119) provides statistical power for bootstrap CIs and McNemar's test
- 80 test surges is sufficient for reliable AUC estimation

**However, the `split_timestamp` value (1,628,120.6) is suspicious** — it doesn't correspond to a recognisable date in any standard time unit. This needs investigation:
- What unit is `created_utc` in the raw CSV? (seconds since epoch? kiloseconds?)
- Did the fix that reduced exclusion rate also change how the split point is reported?
- Is there a mismatch between how the split is computed internally vs how it's serialised to JSON?

## Questions to investigate

1. What code change between July 8 and July 9 altered the timestamp handling?
2. Is the windowing logic now correctly using 24 hours (86,400 seconds) for the forward/backward window?
3. Does the `split_timestamp` reporting need fixing to output a human-readable value or consistent unit?
4. Given sentiment_score achieves AUC=0.968 alone — is this genuine signal or potential leakage? (Sentiment is computed from post text, which is available at observation time, so no leakage by construction. But the strength warrants investigation — are surge posts systematically longer/more emotional in ways that VADER captures?)
