## Observation: Two runs produce radically different results

Comparing `2026-07-08_pipeline_summary.json` and `2026-07-09_pipeline_summary.json` reveals a massive divergence across every metric despite identical config parameters (τ=1.5, w₂=0.5, min_window_count=3, seed=42, sentiment_model=vader).

## Root cause: `split_timestamp` unit mismatch

| | July 8 run | July 9 run |
|---|---|---|
| `split_timestamp` | 1,628,120,809.2 (Unix seconds — Aug 4, 2021) | 1,628,120.6 (not a standard unit) |

The July 8 split timestamp is a valid Unix epoch (seconds). The July 9 value is ~1000× smaller, suggesting a unit conversion change in how the temporal split point is computed or how timestamps in the dataset are being interpreted (seconds vs milliseconds, or a division applied somewhere).

## Investigation Evidence

### 1. Code analysis: `.astype("int64") // 10**9` behavior depends on column dtype

The windowing, labelling, and sentiment modules all convert timestamps the same way:

```python
epoch_seconds = df["created_utc"].astype("int64") // 10**9
```

This produces **correct results only if `created_utc` is `datetime64[ns, UTC]`** (nanoseconds internally). The behavior changes based on what dtype the column has:

| `created_utc` dtype | `.astype("int64") // 10**9` result | Correct? |
|---|---|---|
| `datetime64[ns, UTC]` (from fresh pipeline run) | `1628121600` (Unix seconds) | ✓ |
| `object` / string (from reading saved CSV) | **ValueError** — crashes | ✗ |
| `float64` (epoch seconds as numbers) | `1` (divides seconds by 10⁹ again) | ✗ |

Verified empirically:
```
>>> pd.to_datetime("2021-08-05", utc=True).value // 10**9
1628121600  ← correct

>>> int(1628121600.0) // 10**9
1  ← wrong (double-division)
```

### 2. The saved `labelled_dataset.csv` stores timestamps as strings

```
$ head -1 output/processed/labelled_dataset.csv | created_utc column
"2021-01-01 00:13:41+00:00"   ← dtype: object when re-read
```

When `pd.read_csv()` loads this, `created_utc` becomes a string column. The windowing code would crash on `.astype("int64")`. This means the July 9 run could NOT have been produced by reading the saved CSV directly through the same pipeline path.

### 3. `training.py` vs other modules: inconsistent timestamp parsing

`training.py` (line 172) is defensive:
```python
epoch_seconds = pd.to_datetime(df["created_utc"], utc=True).astype("int64") // 10**9
```

But `windowing.py`, `labelling.py`, and `sentiment.py` assume the column is already datetime64:
```python
epoch_seconds = df["created_utc"].astype("int64") // 10**9
```

This inconsistency means the code works when run fresh (loader guarantees datetime64), but could break if any intermediate step changes the dtype.

### 4. Forward count distribution confirms July 8 run is correct

From direct analysis of the July 8 output:
- 80,212 total records across 11,739 unique tickers
- Median posts per ticker: 2 (half of all tickers appear only 1–2 times in the entire year)
- 4,973 tickers (42%) appear only once ever
- 69% of records have `forward_count = 0` (no future posts for that ticker within 24h)
- Only 11% of records have `forward_count ≥ 3`

This matches the known long-tail distribution of penny stock discussion: a few tickers (GME, AMC) dominate, while most are mentioned once and forgotten.

### 5. The July 9 `split_timestamp = 1,628,120.6` is a broken value

`1,628,120,809 / 1000 ≈ 1,628,120.8` — the July 9 value is approximately the correct timestamp divided by 1000. This is consistent with the "double-division" hypothesis: timestamps that were already in seconds got divided by 10⁹, collapsing all values to ~0-1, and `np.percentile` on those near-zero values produced the fractional result.

With all timestamps collapsed to ~0-1, the window comparison `times + 86400` encompasses the entire dataset — every record appears to be "within 24h" of every other record, giving inflated forward counts and only 29% exclusion.

## Conclusion

**The July 8 run (89% exclusion) is the correct run.** It was produced by running the full pipeline from the raw CSV through the loader (which correctly parses timestamps to `datetime64[ns, UTC]`).

**The July 9 run (29% exclusion) had a timestamp unit bug** where `created_utc` arrived at the windowing stage as numeric epoch seconds (float64) rather than datetime64. The `.astype("int64") // 10**9` division converted ~1.6 billion (seconds) into ~1 (unitless), making all 80k records appear to be within the same 24h window. This caused:
- Massively inflated forward counts → low exclusion rate
- Records from months apart treated as temporally adjacent → data leakage
- AUC values of 0.97+ that reflect leakage, not genuine predictive signal
- Sentiment appearing as the dominant feature (because forward-looking sentiment was being computed across incorrect time windows)

**The July 9 results (AUC 0.97+) are invalid and should be discarded.**

### Implications for the project

1. The 89% exclusion rate is genuine and reflects the sparse, long-tail nature of the r/pennystocks dataset
2. The 7 test surges in the July 8 run is a real statistical limitation — evaluation metrics (especially precision/recall) are unreliable with so few positives
3. Options to improve: lower `min_window_count` to 2 (gives 12,877 included records), or accept the sparse test set and rely primarily on AUC-ROC with bootstrap CIs
4. A defensive fix should be added: explicitly parse timestamps in windowing/labelling/sentiment modules (like training.py already does) to prevent dtype-dependent bugs
