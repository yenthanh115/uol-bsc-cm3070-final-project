# X1 — Target accidentally available in predictors

**Severity: FATAL**
**Failure mode:** Target accidentally available in predictors (model effectively sees the answer).
**Final validation:** Trace every feature column back to its timestamp/source and prove none contains target/future information.

**Verdict: PASS** (no target or forward-window quantity appears in the feature set)

## Method

Traced each of the 11 columns in `FEATURE_COLUMNS` (`src/surge_pipeline/features.py`) back to its computation, and confirmed the target's forward-window inputs are excluded from that set.

## The target and its forward-window inputs (what must NOT leak in)

From `windowing.compute_windowed_counts()` and `labelling.apply_labelling()`:

- `forward_count` — posts in the **forward** window `(t, t+24h]` (future).
- `posting_volume_growth` = `forward_count / max(backward_count, 1) − 1` (uses the future).
- `sentiment_change` / forward mean sentiment (uses the future).
- `surge_label` — the composite z-score thresholded target `y`.

These are the target-defining / future quantities. None of them may appear as a predictor.

## Feature-by-feature trace (all 11 use information at or before t)

| # | Feature | Source in code | Timing | Uses target/future? |
|---|---|---|---|---|
| 1 | `sentiment_score` | copy of `sentiment_polarity` (VADER on own post text at creation) | at t | No |
| 2 | `hour_of_day` | `created_utc.dt.hour` | at t | No |
| 3 | `day_of_week` | `created_utc.dt.dayofweek` | at t | No |

| 6 | `ticker_post_acceleration` | `_compute_ticker_post_acceleration`: two **backward** 12h halves `(t−12h,t]` / `(t−24h,t−12h]` via `searchsorted` | before t | No |

Every feature derives from either the record's own creation-time content (features 1–3, 7–9) or from strictly earlier same-ticker posts (features 4–6), or is a product of those (10–11).

## Proof the target/future columns are excluded

- `FEATURE_COLUMNS` (the exact model input set, returned by `get_feature_matrix`) contains only the 11 columns above. It does **not** contain `forward_count`, `posting_volume_growth`, `sentiment_change`, or `surge_label`.
- The one quantity shared between a feature and the target is `backward_count`: it is feature #5 **and** appears in the label's denominator. This is legitimate — `backward_count` is strictly past information `(t−24h, t)` excluding self; it is not the target and carries no future information. The label's *future* component (`forward_count`) is never exposed as a feature.
- Post-hoc engagement fields (`score`, `num_comments`) are explicitly excluded and asserted by test `test_features_exclude_score_and_num_comments` (`"score" not in FEATURE_COLUMNS`, `"num_comments" not in FEATURE_COLUMNS`).

## Code-level guards against accidental leakage

- `compute_features` validates the required input columns and **asserts global chronological order** (`np.diff(epoch) < 0` → `ValueError`), so backward-only features cannot be silently computed on mis-ordered data.
- `windowing` applies the same chronological assertion before its `searchsorted` counting.
- Backward window uses `side='left'` at the right boundary and forward window uses `side='right'` at the left boundary, so the self-post is excluded from both counts.
- Report corroboration: `@sec:feature-engineering` and `@tbl:feature-detail` state all eleven features are backward-looking/concurrent; `@lst:feature-contract` shows the leakage-contract tests.

## Residual note (not a leakage defect)

The report's own limitations flag a *structural correlation* between `sentiment_score` (current sentiment at t) and the target (which includes forward sentiment *change*). This is a circularity that may inflate sentiment's apparent importance, but it is **not** target-in-predictor leakage: the feature uses only sentiment measured at t, while the target uses the forward-window shift. X1 concerns the target/future value appearing in a predictor, which does not occur.
