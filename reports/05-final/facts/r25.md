# R25 — Prediction errors are analysed

**Requirement:** False positives and false negatives are examined rather than reporting aggregate scores only.
**Priority:** SHOULD
**Assessed:** 2026-09-05
**Verdict:** **PASS**

R25 asks that the evaluation goes beyond aggregate scores to examine the two error types (false
positives and false negatives). The project does this three ways: a dedicated narrative Error
Analysis section that treats FN and FP separately with distinct causal explanations, confusion
matrices that decompose the aggregate into TP/FP/FN/TN, and a re-runnable tool that surfaces
concrete FP/FN example records with saved artefacts.

---

## 1. Dedicated error-analysis section (FP vs FN examined separately)

Report `@sec:error-analysis` analyses the best `WSB` operating point (XGBoost, threshold 0.85),
explicitly splitting the errors and giving each a distinct mechanism rather than a single
aggregate:

- **False negatives (511 missed surges):** concentrate where the backward signal is weakest —
  cold-start surges from tickers with little/no prior 24h activity (`time_since_previous`
  undefined/large, `ticker_post_rate_24h`/`ticker_post_acceleration` near zero), plausibly driven
  by external news outside the forum, and "the dominant missed case given recall of just 0.235."
- **False positives (565 false alarms):** concentrate where precursors resemble a surge but none
  follows — "a burst of accelerating, emotionally charged discussion that fizzles out," plus a
  share from ticker-extraction noise (common uppercase tokens mis-read as tickers).

The section explicitly ties both error types back to design limits (exclusion of external-news
and network signals; the intrinsic difficulty of separating a surge from an aborted build-up),
which is analysis of *why* the errors occur, not just their counts.

## 2. Confusion matrices decompose the aggregate into error types

Errors are quantified per type, not just summarised by a headline metric:

- `@tbl:confusion` — best model at tuned threshold: WSB XGBoost TP=157, FP=565, FN=511,
  TN=67,690; pennystocks RF TP=3, FP=12, FN=28, TN=3,235.
- `@fig:confusion-matrix` — the XGBoost confusion matrix figure, captioned around the 157 TP /
  565 FP / 511 FN split.
- `@tbl:perf-default` reports full confusion-matrix-derived metrics per model, and the operational
  section frames the FP cost ("~1 true positive per 4.6 flags").

These are produced by the evaluation pipeline (`evaluation.py` computes `confusion_matrix`;
`evaluation_figures.py` renders the confusion-matrix plot), so the error decomposition is a
pipeline artefact, not a one-off.

## 3. Concrete FP/FN example records (code + saved artefacts)

`src/generate_prediction_examples.py` is a dedicated tool that loads a saved model, scores the
test partition, and extracts sample records for each outcome:

```python
tp_mask = (y_true == 1) & (y_pred == 1)
fp_mask = (y_true == 0) & (y_pred == 1)   # false positives
fn_mask = (y_true == 1) & (y_pred == 0)   # false negatives
...
results = {
    "true_positives": ..., "false_positives": ..., "false_negatives": ...,
    "counts": {"TP": ..., "FP": ..., "FN": ..., "TN": ...},
}
```

Each example includes context (`id`, `ticker`, `created_utc`, `title`) plus the feature values and
predicted probability, and FN cases are deliberately sorted by *lowest* probability (the
hardest-missed surges) while FP/TP are sorted by highest — i.e. the tool is built to inspect the
error cases, not just tabulate them. It applies the same validation-tuned threshold used in the
evaluation.

**Saved artefacts confirm it was run:**
`output/evaluation/prediction_examples_A2_xgboost.json` and
`output/evaluation/prediction_examples_A1_rf.json` exist, giving concrete FP/FN records for the
main models.

## Verdict

**R25: PASS.** The evaluation examines false positives and false negatives explicitly — a
dedicated Error Analysis section attributes each error type to a distinct, design-linked cause;
confusion matrices and per-model confusion counts decompose the aggregate into TP/FP/FN/TN; and a
re-runnable tool (`generate_prediction_examples.py`) extracts concrete FP/FN example records, with
saved artefacts on disk. This clearly exceeds "aggregate scores only."

### Minor observations (not blocking)

- R25 is a SHOULD; the project goes beyond it by additionally connecting the error patterns to the
  operational deployment argument (`@sec:operational-precision`) and to specific feature/design
  limits.
- The saved prediction-example artefacts cover the two tree models (RF, XGB); the report's
  narrative error analysis centres on the best model (XGBoost on WSB), which is the appropriate
  focus.
