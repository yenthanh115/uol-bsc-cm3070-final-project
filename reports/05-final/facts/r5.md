# R5 — End-user/problem justification exists

**Requirement:** End-user/problem justification exists
**Acceptance / validation criterion:** Identified users, their decision problem, and why
earlier detection could help them are evidenced and connected to requirements.
**Priority:** MUST
**Assessed:** 2026-09-05
**Verdict: PASS**

The report identifies three concrete user groups, states each group's decision problem and
the shortcomings of current practice, explains why *earlier* detection helps them, and then
traces those needs through to explicit requirements, design goals, and operational
acceptance criteria. The connection is not merely narrative: the acceptance criteria are
derived from analyst throughput and one of them (precision ≥ 0.10) is implemented directly
as a threshold-selection strategy in the codebase, closing the loop from user need to code.

Because R5 is fundamentally a justification/design requirement, the primary evidence is in
the report; the codebase provides a corroborating link showing the user-derived criteria are
operationalised rather than only asserted.

## Evidence from the report (`final-report-v0.0.2.md`)

### 1. Users are explicitly identified

[@sec:problem-motivation] names three user groups and is reinforced by the pain-point table
[@tbl:pain-points]:

- **Market surveillance / compliance teams** — prioritise which tickers warrant
  investigation for unusual or potentially coordinated activity.
- **Quantitative researchers** — select a small set of tickers for deeper financial and
  textual analysis.
- **Platform moderators** — position monitoring capacity before discussion spikes.

### 2. Each user's decision problem is stated

[@tbl:pain-points] ("End-user pain points and the shortcomings of current practice") gives,
per group, the decision problem and why current practice falls short:

- Surveillance: thousands of tickers discussed daily must be triaged, but surges develop
  too fast for manual review; rule-based `+2σ` volume alerts miss non-linear, multi-signal
  precursors and cannot rank candidates.
- Researchers: a small set must be chosen from a large, noisy universe; manual scanning is
  slow, subjective, and surfaces tickers only after they are already prominent.
- Moderators: capacity must be positioned *before* spikes; reactive moderation begins once
  a spike is already underway, when intervention is hardest.

The section also makes explicit that the three groups have **different error tolerances**
(surveillance/moderation need high recall; research can accept higher-precision, smaller
shortlists) — a per-user characterisation of the decision problem.

### 3. Why *earlier* detection helps is evidenced

- The Introduction/Background ([@sec:background]) argues that current tools flag a trend
  "once it is already widespread, by which point the chance to analyse, act on, or moderate
  the movement has usually passed", so "anticipating these shifts before they peak is far
  more valuable than confirming them afterwards."
- The shared need is framed as an "early, ranked shortlist" that compresses the candidate
  universe into a reviewable queue while leaving causal judgement to the human reviewer.
- The claim that earlier signals are actionable is grounded in cited literature: Reddit
  attention *preceded* trading activity [15] and consensus formation showed measurable
  patterns *before* reaching critical mass [16] (Literature Review, Financial Discussion
  on Reddit).

### 4. Connected to requirements, objectives and acceptance criteria

The user needs are traced forward, not left as motivation:

- **Objectives** ([@tbl:objectives], [@sec:aim]) — O1 Predict / O2 Compare / O3 Validate
  temporally each carry a success test, derived from the stated aim of helping these users.
- **Design goals** ([@tbl:design-goals], [@sec:requirements]) — the table's first column is
  the user/domain need and it is traced through the requirement it imposes to the design
  response (e.g. moderators needing to act before spikes → "Early prediction" requirement →
  forward-looking 24h target).
- **Operational acceptance criteria** ([@tbl:acceptance-criteria], [@sec:operational-criteria])
  — thresholds are explicitly *derived from workflow constraints*: an analyst reviews ~20–30
  flagged tickers/day against 500–800 daily WSB tickers, giving the daily-alert-volume,
  recall ≥ 0.50, precision ≥ 0.10, and AUC ≥ 0.80 targets.
- **Assumptions** ([@tbl:assumptions]) — Assumption 1 (human-in-the-loop prioritisation) and
  Assumption 2 (~20–30 flagged tickers/day) explicitly anchor the design to the user model.
- **Evaluation back to users** ([@sec:operational-precision]) — results are interpreted per
  user scenario (compliance, quant research, moderators), closing the loop from motivation
  to measured outcome.

## Evidence from the codebase (`src/`)

R5 is a justification requirement, but the user-derived acceptance criteria are
operationalised in code, which corroborates the "connected to requirements" clause.

### `surge_pipeline/evaluation.py` — user precision target implemented as a strategy

The operational criterion *precision ≥ 0.10* ([@tbl:acceptance-criteria], derived from the
"no more than ~9 false alarms per true positive" analyst-workflow rationale) appears directly
as a threshold-selection strategy with a matching default:

```python
def find_optimal_threshold(
    y_true, y_prob, model_name="Model",
    strategy="max_f1",
    precision_floor: float = 0.10,   # matches the ≥ 0.10 acceptance criterion
):
    ...
    #   - "precision_floor": Find the lowest threshold where
    #     precision >= precision_floor, then maximise F1 among those candidates.
    if strategy == "precision_floor":
        valid_mask = precisions >= precision_floor
        ...
```

This is the user-facing precision floor (10%) baked into the operating-point selection logic,
showing the acceptance criterion is enforced, not just stated.

### Screening/ranking framing reflected in the pipeline

The reporting stack (`run_training.py`, `run_cross_validation.py`, `evaluation.py`) computes
and prints **precision, recall, F1 and AUC-ROC at both default and tuned thresholds** — the
exact metric set the acceptance criteria are written against. Threshold tuning is documented
as producing an *operating point*, matching the report's "prioritisation tool / ranked
shortlist" framing for the three user groups rather than an autonomous decision-maker.
