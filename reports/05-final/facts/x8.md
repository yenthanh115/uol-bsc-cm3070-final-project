# X8 — Threshold selection is unjustified

**Severity:** CRITICAL
**Failure mode:** Threshold selection is unjustified — in particular quietly choosing the
classification threshold that maximises a metric *on the test set*.
**Why dangerous:** Precision/recall/F1 can change substantially with threshold, so a
test-tuned threshold inflates reported operating-point performance.
**Final validation:** State how the classification threshold was selected; don't quietly
choose the best test threshold.
**Assessed:** 2026-09-05
**Status:** **PASS**

X8 is CRITICAL and was checked against both the code and the report. The decision threshold is
selected by a documented rule (maximise F1) on the **validation fold**, then applied
**unchanged** to the held-out test set. The test set is never used to choose the threshold, and
the report both states the selection method and reports default-0.5 and tuned metrics side by
side, so nothing is quietly optimised against the test set.

---

## 1. The selection rule is explicit and documented ✔

`evaluation.find_optimal_threshold()` sweeps thresholds `0.01…0.99` and selects by a stated
strategy (default `max_f1`; a `precision_floor` variant also exists). Its own docstring states
the discipline:

> "Sweeps thresholds from 0.01 to 0.99 and selects the best operating point based on the chosen
> strategy. This should be called on a **validation set** (not the test set) to avoid
> optimistic bias."

The report states the same rule (`@sec:temporal-validation`): "$F_1$-optimised decision
thresholds are locked on validation folds and applied unchanged to the test set, ensuring
uncontaminated final evaluation," and (`@sec:eval-pipeline`) "Threshold tuning maximises $F_1$
on the last validation fold and is applied unchanged to the test set, so no test information
informs the operating point."

## 2. The threshold is selected on VALIDATION data, not test ✔

In `run_training.py` the caller passes the **last CV validation fold's** labels/probabilities,
not the test set:

```python
for name, tm in training_result.models.items():
    if tm.val_y_true is not None and tm.val_y_prob is not None:
        # Select optimal threshold on the last CV validation fold
        tr = find_optimal_threshold(tm.val_y_true, tm.val_y_prob, model_name=name)
        # Apply tuned threshold to test set
        y_pred_tuned = predict_with_threshold(probabilities[name], tr.optimal_threshold)
```

- `tm.val_y_true` / `tm.val_y_prob` are produced in `training.py` from the last expanding-window
  validation fold: `final_scaler.transform(X_train_full[last_val_idx])` →
  `final_model.predict_proba(...)`. These indices come from **within the training partition**
  (`splits[-1]`), so they are genuinely unseen by threshold *selection* yet never part of the
  held-out test set.
- `probabilities[name]` are the **test-set** probabilities; the validation-chosen
  `tr.optimal_threshold` is applied to them by `predict_with_threshold` — a fixed number applied
  to test, not re-optimised on test.

So the operating point is fixed before the test set is scored at it. This mirrors the leakage
prevention already established for scalers in X2.

## 3. Both default and tuned metrics are reported transparently ✔

The pipeline reports metrics at the **default 0.5** threshold *and* at the validation-tuned
threshold, and prints the provenance line "(Threshold selected on validation fold:
val_F1=…)". The saved `*_threshold_tuning.json` records, per model:
`optimal_threshold`, the validation-fold metrics at that threshold, and the test-set metrics at
both the tuned and default-0.5 thresholds. The report's `@tbl:perf-default` (0.5) and
`@tbl:perf-tuned` (validation-tuned, e.g. WSB XGB 0.85, pennystocks XGB 0.16) show both, so the
threshold's effect is visible rather than hidden.

This transparency is corroborated by the R36 live run, whose tuned thresholds and F1 deltas
matched `@tbl:perf-tuned` for pennystocks (e.g. XGB tuned at 0.16, F1 ≈ 0.121; RF tuned ~0.79),
and which printed the "selected on validation fold" provenance for each model.

## 4. The operating-point *choice* is justified, not arbitrary ✔

Beyond the mechanics, the report justifies *why* a threshold is needed and how the operating
point should be read: `@sec:operational-criteria` derives acceptance thresholds from analyst
throughput, and `@sec:operational-precision` evaluates the best model against them and shows the
tuned point (XGB 0.85 on WSB) meets AUC/precision but not recall — explicitly *not* cherry-picking
a flattering test threshold. AUC-ROC (the primary, threshold-independent metric) is reported
alongside, so the headline result does not depend on threshold choice at all.

## Status

**X8: PASS.** Threshold selection is justified and leakage-free. The classification threshold
is chosen by a documented rule (maximise F1, sweeping 0.01–0.99) on the **last validation fold**
inside the training partition, then applied unchanged to the held-out test set via
`predict_with_threshold`; the test set is never used to pick the threshold. The report states
this method (`@sec:temporal-validation`, `@sec:eval-pipeline`), reports both default-0.5 and
validation-tuned metrics (`@tbl:perf-default`, `@tbl:perf-tuned`), persists the choice in
`*_threshold_tuning.json`, and justifies the operating point against throughput-derived
acceptance criteria while reporting the threshold-independent AUC-ROC as the primary metric.
Nothing is quietly optimised against the test set.

### Minor observations (not blocking)

- The tuned threshold is selected on a *single* validation fold (the last expanding-window
  fold) rather than pooled across folds. This is a reasonable, deployment-realistic choice
  (most-recent data) and is disclosed; it can make the operating point somewhat variable, which
  the report acknowledges via the validation-to-test F1 gap in `@sec:temporal-stability`. It does
  not affect X8, since the threshold is still chosen off-test.
- A `precision_floor` strategy exists in `find_optimal_threshold` but the reported results use
  `max_f1`; this is stated, not hidden.
