# X7 — Hyperparameter/model selection indirectly optimised against final test set

**Severity: CRITICAL**
**Failure mode:** Hyperparameter/model selection indirectly optimised against the final test set (test set ceases to be independent).
**Final validation:** Verify test results were not repeatedly used to choose model/features/thresholds.

**Verdict: PASS** (hyperparameter, model, and threshold selection are all performed on within-train validation folds; the test set is scored once per config and never used as a selection signal — with one disclosed pipeline-level design decision noted below)

## Hyperparameter selection is validation-based (code)

`training._train_single_model()` chooses `best_params` purely from cross-validation on the **training** partition:

```
for params in param_grid:
    for train_idx, val_idx in splits:          # expanding-window folds within TRAIN
        scaler.fit(X_train_full[train_idx]) ; transform(val)
        model.fit(fold_train) ; y_prob = predict_proba(fold_val)
        fold_aucs.append(roc_auc_score(y_fold_val, y_prob))   # validation AUC
    mean_auc = mean(fold_aucs)
    if mean_auc > best_mean_auc: best_params = params
# retrain best_params on full TRAIN partition
```

The selection criterion is mean **validation-fold** AUC. `X_test`/`y_test` are never referenced inside `_train_single_model` or `train_models`, so no hyperparameter is chosen using test performance.

## Threshold selection is validation-based (code)

The operating threshold comes from `find_optimal_threshold(tm.val_y_true, tm.val_y_prob, ...)`, where `val_y_true`/`val_y_prob` are the **last CV validation fold** (within train). The function's own docstring states it "should be called on a **validation set** (not the test set) to avoid optimistic bias." The chosen threshold is serialised with the model and applied unchanged at test time.

## Model selection is not test-cherry-picked

All three model families (LR, RF, XGB) are trained and **all** are reported in `@tbl:perf-default`/`@tbl:perf-tuned`; the "best model" per dataset is identified by CV AUC and reported alongside the others, not selected by scanning test scores and hiding the rest.

## Test set is scored once per configuration (report)

- `@sec:temporal-validation`: the held-out test set is "evaluated exactly once"; "$F_1$-optimised decision thresholds are locked on validation folds and applied unchanged to the test set, ensuring uncontaminated final evaluation."
- `@sec:eval-pipeline`: "Threshold tuning maximises $F_1$ on the last validation fold and is applied unchanged to the test set, so no test information informs the operating point."
- Runs are config-driven and logged (`experiment_log.jsonl`): sweeps over threshold $\tau$ and sentiment weight $w_2$ are executed by re-running with different configs, each producing its own labelled dataset + train/test split — they are reported as **sensitivity analyses across the whole pipeline**, not as knobs tuned to maximise a fixed test set.

## Disclosed design decision (noted, not a failure)

The experiment log and `@sec:` "Implementation Decisions Driven by Empirical Findings" record that the project scaled from `r/pennystocks` (~80k records) to `WSB` after observing that at higher thresholds the *sparse* setting produced as few as 7 positive **test** examples, making metric estimates unstable. This decision was informed by observing test-side positive **counts** (a data-adequacy/stability concern), not by choosing the configuration with the highest test AUC. The threshold $\tau=1.5$ is presented as the primary operating point with $\tau=1.0$ retained for sensitivity, and the full $\tau$ and $w_2$ sweeps are reported transparently. This is a mild researcher-degrees-of-freedom exposure that the report discloses rather than conceals; it does not constitute repeatedly tuning model/feature/threshold choices against the final test metric.

## Why PASS rather than PARTIAL

The X7 failure is "test results repeatedly used to choose model/features/thresholds." In this pipeline:
- model choice, hyperparameters, and threshold are all selected on validation folds (provable in code);
- the test set is evaluated once per config and its metrics are not the selection objective;
- the multi-config runs are disclosed sensitivity sweeps, and the headline results are reported with bootstrap CIs and significance tests.

The single pipeline-level decision (dataset scaling for positive-count stability) is documented and is not test-AUC optimisation. On balance the test set remained independent for all selection steps.
