# X3 — Same underlying event/entity leaks across train/test

**Severity: FATAL**
**Failure mode:** Same underlying event/entity leaks across train/test (different rows may actually represent the same trend episode).
**Final validation:** Check whether observations derived from the same event/window/topic can occur on both sides of the split.

**Verdict: PASS** (split is per-record and chronological; no shared row/episode crosses the split; window overlap at the boundary is a bounded label-construction effect, not entity/episode contamination)

## How the split works (code)

- `labelling._temporal_split()` sorts records by `created_utc` (epoch seconds) and assigns `partition = "train"` where `epoch <= split_ts` else `"test"`, with `split_ts = percentile(epoch, ratio*100)`. Boundary ties deliberately go to **train** (`<= split_ts`), so the boundary instant is never treated as test/future.
- No shuffling; the split is a single chronological cut. `training.create_temporal_folds()` likewise builds contiguous chronological blocks (argsort by timestamp), so CV folds are time-ordered too.
- Unit of analysis is the exploded **record–ticker pair**; each row corresponds to a unique Reddit submission id at a unique timestamp.

## Facet 1 — same entity (ticker) appearing in both partitions → NOT leakage

The same ticker (e.g. `$AMC`) is discussed across 2021 and therefore appears in both the early (train) and late (test) partitions. This is **expected and correct** for a temporal forecaster: the task is to predict *future* surges for tickers whose past discussion is observable. A recurring entity at different times is not "the same episode"; it is the same entity at genuinely later, unseen times. This is not the X3 failure.

## Facet 2 — window overlap at the split boundary → bounded, not contaminating

Features use a 24h **backward** window and the target uses a 24h **forward** window, so a thin band of records around `split_ts` has windows that overlap the boundary. Examined in both directions:

- **Test record just after the split**: its backward window `(t−24h, t)` may count *training-era* posts. This is legitimate — at deployment those past posts are always available at scoring time. Past→present information is not leakage.
- **Training record just before the split**: its *label* forward window `(t, t+24h]` may include *test-era* posts. But a label is the **target**, computed once per record from that record's own future window; it is never a model input, and the model never trains on test rows. So no test observation, test feature, or test label is exposed to the model. At worst a few near-boundary training **labels** are informed by posts occurring shortly after the split — a mild, well-understood boundary effect that, if anything, perturbs a handful of training targets rather than inflating test performance.

Crucially, **no single row (post–ticker pair) appears on both sides**: the split partitions rows by their own timestamp, rows are unique per submission id, and there is no episode-level expansion that would duplicate one event into multiple correlated rows straddling the split.

## Supporting mitigations (code + report)

- **Boundary-past-dataset exclusion** (report `@sec:surge-definition`, corroborated by `@tbl:loader-attrition` narrative): records are excluded as unlabellable when (1) the forward 24h window has `< 2` same-ticker posts or (2) the forward window extends beyond the dataset's final timestamp — so degenerate near-end windows do not produce spurious labels.
- **Training-only normalisation**: μ/σ for `posting_volume_growth` and `sentiment_change` are computed from the training partition only (`apply_labelling` Step 2), then applied to all records — no test distribution information flows into labels.
- **No deduplication needed**: loader maps each raw row to a unique submission id (report Data Loading Step 1), so identical posts cannot land on both sides.
- **Single-use holdout + expanding-window CV** (`@sec:temporal-validation`): the test partition is evaluated once and all CV folds preserve `max(train_ts) < min(val_ts)`, isolating test evaluation from any boundary label effect.

## Residual note

The only boundary interaction is that a small number of *training-set labels* near the split are constructed from forward-window posts occurring just after `split_ts`. This affects label construction for training rows only; it does not place any test row, test feature, or test label into training, and does not create correlated duplicate rows across the split. It is therefore not the shared-event/entity contamination X3 targets. (Distinct from X4/X6, which cover label-timing and feature-availability and are assessed separately.)

## Summary

| Check | Result |
|---|---|
| Split partitions rows by their own timestamp (chronological, no shuffle) | Yes |
| Same physical row (post–ticker) can appear on both sides | No (unique ids; single time cut) |
| Same ticker in both partitions | Yes — expected for temporal forecasting, not leakage |
| Same episode duplicated into correlated rows straddling the split | No episode-level expansion exists |
| Near-boundary forward-window labels leak test features/labels into training | No (labels are targets, model never sees test rows) |
| Degenerate/near-end windows handled | Yes (excluded as unlabellable) |

**X3 = PASS**
