# R10 — Class distribution is analysed

**Requirement:** Class distribution is analysed
**Acceptance / validation criterion:** Number/proportion of surge and non-surge observations
is reported and implications of imbalance are considered.
**Priority:** MUST

**Verdict: PASS**

The class distribution is both computed by the pipeline and reported/analysed in depth. The
code produces surge/non-surge **counts**, **proportion (surge rate)** and **imbalance ratio**
for the overall, training and test partitions, writes them to the run summary, and exposes
them across the threshold sweep with a viability flag. The report states the exact numbers
(668 surges / 68,923 records = 0.97%, 102:1 on WSB; 31 / 3,278 = 0.95%, 105:1 on
`r/pennystocks`) and repeatedly reasons about what the imbalance means — for metric choice,
model behaviour, operating-point selection, and deployment. Both halves of the criterion,
"number/proportion reported" and "implications considered", are satisfied.

---

## Evidence from the codebase (`src/`)

### 1. Class distribution is computed per partition — `labelling.py`

`_compute_class_distribution()` returns counts, proportion and imbalance ratio, and logs them:

```python
surge_count      = int((valid == 1).sum())
no_surge_count   = int((valid == 0).sum())
total            = len(valid)
surge_rate       = surge_count / total * 100 if total > 0 else 0.0
imbalance_ratio  = no_surge_count / surge_count if surge_count > 0 else float("inf")
...
logger.info(
    "Class distribution [%s] — surge: %d | no-surge: %d | "
    "total: %d | surge rate: %.2f%% | imbalance ratio: %.2f:1", ...
)
```

`apply_labelling()` calls this for the **all (included)**, **train**, and **test** partitions
and returns them in `LabellingResult.class_distributions`, so distribution is analysed
separately for the very partitions used to train and evaluate.

### 2. Distribution is persisted and surfaced — `pipeline.py`, `run_labeling.py`

- `run_pipeline()` returns `class_distributions`, and `save_outputs()` writes them into the
  `*_pipeline_summary.json` audit artefact.
- The `run_labeling.py` CLI prints the class distribution block (surge / no-surge / surge rate
  / imbalance) to the console at the end of every full run.

### 3. Distribution is analysed across thresholds with a viability flag — `pipeline.py`

`run_threshold_sweep()` / `_sweep_results_to_rows()` build a per-threshold table with columns
`threshold, surge_count, no_surge_count, surge_rate, imbalance_ratio, viable`, where
`viable = 5.0 <= surge_rate <= 10.0`. This is an explicit analysis of how the class balance
changes with the surge definition and whether the positive class remains learnable:

```python
rows.append({
    "threshold": tau,
    "surge_count": surge_count,
    "no_surge_count": no_surge_count,
    "surge_rate": surge_rate,
    "imbalance_ratio": imbalance_ratio,
    "viable": 5.0 <= surge_rate <= 10.0,
})
```

The sweep table is logged, saved to `*_threshold_sensitivity.csv`, and the run warns when
"No viable thresholds found".

### 4. Imbalance implications are acted on in modelling — `training.py`

The measured imbalance is not just reported; it drives the training strategy. The
negative-to-positive ratio is computed from the actual training partition and injected into
the models:

```python
n_positive = int(np.sum(y_train_full == 1))
n_negative = int(np.sum(y_train_full == 0))
imbalance_ratio = float(n_negative) / max(n_positive, 1)
logger.info("Training data: ... surge=%.1f%% | imbalance_ratio=%.1f:1", ...)
```

XGBoost's `scale_pos_weight` grid is `{1, ratio/2, ratio}`, and LR/RF use
`class_weight='balanced'` — i.e. the class distribution directly parameterises imbalance
mitigation.

### 5. Distribution reporting is covered by tests

- `test_pipeline_integration.py::test_class_distributions_present` asserts the results carry
  `class_distributions["all"]` with `surge_count` and `no_surge_count`.
- `test_sweep_has_expected_columns` asserts the sweep exposes
  `{threshold, surge_count, no_surge_count, surge_rate, imbalance_ratio, viable}`.
- `test_sweep_surge_rate_decreases_with_threshold` asserts the surge rate is monotonically
  non-increasing in the threshold — a check on the distribution analysis itself.

## Evidence from the report (`final-report-v0.0.2.md`)

### Numbers / proportions reported

- **[@tbl:dataset-characteristics]** reports, per dataset, usable records, train/test split,
  **test surges** (31 and 668) and **test imbalance ratio** (105:1 and 102:1).
- The **Dataset and Target Analysis** section states the proportions explicitly: WSB "668
  surges in 68,923 test records (0.97%, a 102:1 negative-to-positive ratio)" and
  `r/pennystocks` "31 surges in 3,278 records (0.95%, 105:1)".
- **[@tbl:weight-sensitivity]** and the sentiment-contribution analysis report how the surge
  **rate** shifts with the target weighting (0.53% → 9.62%), and the EDA screening
  ([@tbl:eda-deep]) reports positive-class rates (5.8% / 5.0%).

### Implications of imbalance considered

- **Metric choice:** the sub-1% positive rate is used to justify AUC-ROC as primary and to
  reject accuracy ("a trivial 'never surge' classifier scores 99% accuracy").
- **Model behaviour:** [@sec:complexity-density] links the 105:1/102:1 ratio to XGBoost's
  probability saturation and zero positive predictions at the 0.5 threshold.
- **Operating point:** [@sec:operational-precision] shows no single threshold meets both
  recall and precision targets "at 102:1 class imbalance", motivating rank-based deployment.
- **Estimation uncertainty:** the small positive count on `r/pennystocks` (31) is flagged as
  producing wide bootstrap CIs, in Dataset and Target Analysis and the Limitations.
- **Deployment constraint:** the Limitations section devotes "Class imbalance as deployment
  constraint" to the precision ceiling at sub-1% prevalence and how the surge definition
  could be co-designed to relax it.
- **Design-level handling:** [@sec:model-selection] documents cost-sensitive learning
  (`class_weight='balanced'`, `scale_pos_weight`) and why SMOTE was rejected for temporal data.

(Class-imbalance *handling* is R24's focus; it is cited here only as evidence that the
distribution's *implications* were considered, which is R10's second clause.)
