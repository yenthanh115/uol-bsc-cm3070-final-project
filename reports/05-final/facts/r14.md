# R14 — Sentiment features implemented

**Requirement:** Sentiment features implemented
**Acceptance / validation criterion:** Sentiment is transformed into clearly defined modelling
features and its temporal availability is leakage-safe.
**Priority:** MUST for current design

**Verdict: PASS**

Sentiment is computed once per record (VADER compound score with a title fallback) and turned
into a clearly defined modelling feature, `sentiment_score`, plus two interaction terms that
build on it. The modelling feature uses only the record's own text at creation time, so it is
leakage-safe. The forward-window sentiment quantities (`mean_future_sentiment`,
`sentiment_change`) are used exclusively to build the *target*, never as model features — a
separation that is documented, coded, and enforced by tests. Both halves of the criterion,
"clearly defined modelling feature" and "leakage-safe temporal availability", are satisfied.

---

## Evidence from the codebase (`src/`)

### 1. Sentiment is computed as a clearly defined per-record scalar — `sentiment.py`

`compute_sentiment` produces `sentiment_polarity`, a single VADER compound score per record,
with a documented title-fallback and neutral default:

```python
def _compute_polarity_vader(title, selftext):
    analyzer = _get_vader_analyzer()
    if selftext and str(selftext).strip():
        text = f"{title} {selftext}"       # body present → title + body
    elif title and str(title).strip():
        text = title                        # body absent → title fallback
    else:
        return 0.0                          # no text → neutral
    return analyzer.polarity_scores(text)["compound"]   # compound in [-1, 1]
```

A configurable backend (`sentiment_model`: `vader` default, `textblob` alternative) selects the
scorer, so the transformation is explicit and parameterised, not ad hoc.

### 2. Sentiment becomes an explicit modelling feature — `features.py`

`sentiment_score` is the first of the 11 `FEATURE_COLUMNS`, and it reuses the record's own
observation-time polarity:

```python
# Feature 1: sentiment_score (R11-AC1)
# Reuse sentiment_polarity computed at observation time
df = df.assign(sentiment_score=df["sentiment_polarity"].values.copy())
```

Two documented interaction terms extend it: `word_count_x_hour` and, crucially,
`accel_x_time_since_prev` — while `sentiment_score` itself also feeds the models directly.
`FEATURE_COLUMNS` lists `sentiment_score` explicitly, so the sentiment signal is a
first-class, named modelling input.

### 3. Temporal availability is leakage-safe

Two distinct sentiment quantities exist and are kept on the correct side of time `t`:

- **Feature (leakage-safe):** `sentiment_score` = `sentiment_polarity`, computed from the
  record's *own* title/selftext at creation time. The module docstring states it is
  "Computed strictly from the record's own text at creation time, no forward window
  information." It is in `FEATURE_COLUMNS`.
- **Target-only (forward-looking):** `mean_future_sentiment` and `sentiment_change`
  (= |mean_future − current|) are computed over the forward window `(t, t + 24h]` in
  `sentiment.py`. These are **not** in `FEATURE_COLUMNS`; they feed the composite surge target
  in `labelling.py` (the `z_sentiment` term), never the model's input matrix.

The forward-window computation reuses the same window logic as `windowing.py`:

```python
# Forward window: (t, t + 24h] — same logic as windowing.py
forward_left  = np.searchsorted(times, times, side="right")
forward_right = np.searchsorted(times, times + _WINDOW_SECONDS, side="right")
...
sentiment_change = np.abs(mean_future - polarities)   # target input only
```

So the only sentiment value the model sees is backward/at-time-t; the forward-looking
sentiment shift is confined to label construction.

### 4. Leakage-safety is enforced by tests — `tests/`

- `test_features.py::TestNoFutureLeakage::test_features_exclude_score_and_num_comments`
  asserts post-hoc engagement is excluded from `FEATURE_COLUMNS`; combined with the fact that
  `sentiment_score` maps to `sentiment_polarity` (not `sentiment_change`), the forward sentiment
  never enters the feature matrix.
- `test_sentiment.py` verifies the sentiment transformation itself:
  - polarity sign/range: `test_vader_positive_text`, `test_vader_negative_text`,
    `test_vader_score_in_range` (compound in [-1, 1]);
  - **title-fallback**: `test_vader_title_only_fallback`, `test_title_only_when_selftext_empty`,
    `test_nan_selftext_treated_as_empty`;
  - neutral default: `test_neutral_when_both_empty`;
  - forward-window correctness and that `sentiment_change = |mean_future − current|`
    (`TestMeanFutureSentiment`), plus per-ticker isolation of the forward window;
  - excluded-record handling (`sentiment_change = 0`).

The report notes the full suite passes with zero errors ([@tbl:test-modules], `test_sentiment.py`).

## Evidence from the report (`final-report-v0.0.2.md`)

- **Feature definition:** [@tbl:feature-definitions] and [@tbl:feature-detail] define
  `sentiment_score` as "VADER compound sentiment of the post text", computed by
  `sentiment.compute_sentiment()` "strictly from the record's own text at creation time, no
  forward window information."
- **Leakage-safe separation:** [@sec:data-representation] and the Surge Definition
  ([@sec:surge-definition]) make explicit that current sentiment `s_t` is available at time
  `t`, while the forward mean `S̄_fwd` and `ΔS = |S̄_fwd − s_t|` define the *target*, not a
  feature. The Limitations section states the "feature uses *current* sentiment while the
  target uses *forward-window* shift, not leakage" ([@sec:sentiment-signal] / limitations).
- **Tooling / backend:** [@tbl:sentiment-tools] and the pipeline stages ([@tbl:pipeline-stages],
  stage 3) document VADER with title-fallback; the EDA phase screens VADER vs TextBlob
  agreement as a reliability check ([@tbl:eda-deep]).
- **Design fit:** [@tbl:signal-families] classifies sentiment as an included signal ("sentiment
  level and change"), and the evaluation shows `sentiment_score` is the top permutation-importance
  feature across all models ([@tbl:feature-importance]), confirming it is a live modelling input.
- **Priority context:** the requirement is "MUST for current design"; the composite target and
  feature set both depend on sentiment, so the current design does implement it.

Note on the target–feature correlation: the report transparently flags that `sentiment_score`
(current) is correlated with the sentiment component of the target (forward shift) and calls it
a "circularity" that may inflate apparent importance, but explicitly *not* leakage, since the
feature and target draw on different time windows. This is a documented interpretation caveat,
not a violation of R14's leakage-safety clause.
