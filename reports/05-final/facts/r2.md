# R2 — Trend/surge has an operational definition

**Requirement:** A deterministic rule converts observations into trend/surge vs non-trend labels; parameters and rationale are documented.
**Priority:** MUST
**Assessed:** 2026-09-05
**Verdict:** **PASS**

R2 has three parts: (1) a **deterministic rule** that turns observations into surge vs
non-surge labels, (2) its **parameters** are documented, and (3) its **rationale** is
documented. All three hold, and — checked in this re-assessment — the code implements exactly
the rule the report describes, with every parameter surfaced as a documented, serialised
configuration field.

---

## 1. The rule is deterministic ✔

The surge label is a pure, deterministic function of the data and a fixed configuration —
no randomness, no learned thresholds. The report states it (`@sec:surge-definition`,
`@lst:surge-labelling`) and `labelling.apply_labelling()` implements it step-for-step:

1. Temporal 80/20 split at the 80th-percentile timestamp (`_temporal_split`).
2. Volume growth ΔV and sentiment shift ΔS computed per record-ticker (windowing/sentiment stages).
3. Standardise with **training-partition** μ/σ only (population std, ddof=0):
   `z_volume`, `z_sentiment`.
4. Composite: `composite = (w1 * z_volume) + (w2 * z_sentiment)`.
5. Binary label: `surge_label = np.where(composite > tau, 1.0, 0.0)`.

Given the same input and the same `PipelineConfig`, this yields identical labels every time.
Determinism is further guaranteed by the fixed global seed (default 42) set across `random`,
NumPy and sklearn, and was demonstrated empirically in the R36 live run (pennystocks reproduced
the reported label counts: 24,827 usable = 698 surge / 24,129 no-surge).

## 2. Parameters are documented — and match code ✔

Every parameter of the rule is stated in the report and is a first-class, JSON-serialised
field of `PipelineConfig` (`config.py`), so the definition is auditable and reproducible:

| Parameter | Report (`@sec:surge-definition`) | Code (`PipelineConfig` / `config.py`) |
|---|---|---|
| Observation/target window | 24 h backward `[t-24h, t)`, forward `(t, t+24h]` | `WINDOW_SECONDS = 24*60*60` |
| Temporal split | 80/20 by timestamp | `temporal_split_ratio = 0.8` |
| Volume weight w₁ | 0.5 (Phase 2 composite) | `weight_volume = 0.5` |
| Sentiment weight w₂ | 0.5 (Phase 2 composite) | `weight_sentiment = 0.5` |
| Threshold τ | 1.5 primary; 1.0 secondary | `threshold_tau = 1.5` |
| Threshold sweep | {0.5, 1.0, 1.5, 2.0, 2.5} | `thresholds = [0.5, 1.0, 1.5, 2.0, 2.5]` |
| Normalisation basis | training μ/σ only, population std | `np.std(..., ddof=0)` on `train_mask` |
| Surge rule | `Composite > τ ⇒ y=1` | `np.where(composite > tau, 1.0, 0.0)` |

The config is written to `pipeline_config.json` on every run (`save_json`), so the exact
parameters of any labelling run are persisted for audit.

## 3. Rationale is documented ✔

The report explains *why* the rule is built this way, not just what it is:

- **Why composite, not a fixed count**: "A fixed posting-count threshold fails because tickers
  have different baselines" — hence z-score normalisation of growth relative to the training
  distribution (`@sec:surge-definition`).
- **Why 24 h window**: aligns with daily trading cycles; 6 h too sparse, 72 h blurs onset.
- **Why include sentiment (ΔS)**: hypothesis that rising emotional charge can precede a volume
  spike; earns its place only if it helps, tested via Phase 1 vs Phase 2 (`@sec:sentiment-contribution`).
- **Why τ = 1.5**: trades anomaly purity against class balance; isolates genuine anomalies while
  keeping enough positives, with τ = 1.0 kept for sensitivity analysis.
- **Why training-only μ/σ**: prevents test-set distribution information leaking into labels
  (the leakage-safety rationale, cross-checked by `test_labelling.py`).

## 4. Cross-checks

- **Unit-tested**: `test_labelling.py` verifies the composite formula, threshold labelling at
  known values, and that z-scores use training-only μ/σ (`@lst:leakage-test`).
- **Report ↔ code agreement**: the `@lst:surge-labelling` listing in the report is a faithful
  excerpt of `apply_labelling()` (steps 1–4 identical), so the documented rule is the
  implemented rule.
- **Sweep is deterministic too**: `sweep_thresholds()` re-labels across the documented τ set in
  one vectorised pass, each τ producing a deterministic label set.

## Verdict

**R2: PASS (re-confirmed).** The surge target is defined by a deterministic rule —
`surge_label = 1` iff `w1·Z(ΔV) + w2·Z(ΔS) > τ`, with z-scores standardised using
training-partition statistics only — implemented in `labelling.apply_labelling()` exactly as
the report's `@sec:surge-definition` / `@lst:surge-labelling` describe. Every parameter (24 h
window, 80/20 temporal split, w₁ = w₂ = 0.5, τ = 1.5 with a documented sweep, population-std
normalisation) is a documented, JSON-serialised `PipelineConfig` field, and the rationale for
each choice (per-ticker baselines, daily-cycle window, sentiment hypothesis, anomaly-vs-balance
threshold trade-off, leakage-safe normalisation) is stated in the report. The rule is
unit-tested and was shown deterministic in the R36 live run.

### Minor observations (not blocking)

- `PipelineConfig` also exposes a `surge_method` with a `backward_only` alternative to the
  default `forward_growth`; the report documents only the `forward_growth` composite target used
  for all reported results. The alternative is an implementation option, not part of the
  reported surge definition, so it does not affect R2.
- The report's τ = 1.5 primary / τ = 1.0 secondary framing matches the config default
  (`threshold_tau = 1.5`) and sweep list; no discrepancy.
