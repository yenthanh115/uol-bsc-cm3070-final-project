# R31 — Objectives are individually evaluated

**Requirement:** Conclusion/evaluation returns explicitly to each original objective and states achieved / partially achieved / not achieved with evidence.
**Priority:** CRITICAL
**Assessed:** 2026-09-05
**Verdict:** **PASS**

R31 has four parts: (1) original objectives are defined, (2) the evaluation/conclusion
returns to *each* one explicitly, (3) each gets an explicit verdict on the
achieved/partially-achieved/not-achieved scale, and (4) each verdict is backed by
evidence. All four hold, and the underlying evidence for each verdict is produced by code
in `/src` rather than asserted.

---

## 1. Original objectives are defined

§ Aim, Objectives and Contributions states three objectives, each with an explicit success
test (`@tbl:objectives`):

| # | Objective | Success test (as originally stated) |
|---|-----------|-------------------------------------|
| O1 — Predict | Model from early-stage features that forecasts surges before they occur | Clears the target AUC-ROC tier on held-out future data |
| O2 — Compare | Whether more complex models improve over simpler baselines | Differences quantified with uncertainty and significance |
| O3 — Validate temporally | Whether predictions hold on unseen future periods, leakage-free | No feature/label/statistic draws on future data; results on a chronological holdout |

## 2. The evaluation returns to each objective explicitly

The report contains a dedicated section, **§ Evaluation Against Project Objectives**
([@sec:eval-objectives]), whose sole purpose is to revisit the objectives. Its
`@tbl:objective-verdicts` has one row per objective (O1, O2, O3) — so each original
objective is addressed individually, not collectively. The Conclusion's "Limitations and
Future Work" then reaffirms the outcome ("All three objectives were met
([@sec:eval-objectives])").

## 3. Each objective gets an explicit verdict (achieved / partial / not achieved)

`@tbl:objective-verdicts` assigns an explicit verdict to each:

| Objective | Verdict stated in report |
|-----------|--------------------------|
| O1 — Predict surges | **Met** |
| O2 — Compare approaches | **Met** |
| O3 — Temporal validity | **Met** |

"Met" is the report's label on the achieved/partially-achieved/not-achieved scale. That
the scale is used *discriminatingly* (not a blanket pass) is shown elsewhere in the same
evaluation: the operational acceptance criteria (`@tbl:acceptance-eval`) are explicitly
marked **No** (recall) and **Partial** (alert volume), and the Conclusion enumerates four
limitations that bound the "Met" verdicts. So the objective verdicts are genuine
judgements, not a formality.

## 4. Each verdict is backed by evidence (and the evidence is code-produced)

`@tbl:objective-verdicts` pairs every verdict with a specific evidence pointer, and each
pointer resolves to a results table/section that is in turn produced by pipeline code:

| Objective | Evidence cited in report | Code that produces it | Persisted artefact |
|-----------|--------------------------|------------------------|--------------------|
| O1 Met | Both tree models clear stretch on WSB / target on pennystocks, above best single feature (`@tbl:perf-default`, `@tbl:baselines`) | `evaluation.validate_success_tiers` (tiers 0.60/0.70/0.80), `evaluate_baselines` | `success_tier_achieved`, `tier_results`, `baseline_comparisons` in `*_final_summary.json` |
| O2 Met | All pairwise differences significant; complexity-vs-density inversion (`@sec:statistical-validation`, `@sec:complexity-density`) | `evaluation.mcnemar_pairwise_test`, `compute_bootstrap_ci`, `evaluate_baselines` | `mcnemar_results`, CI fields in `*_final_summary.json` |
| O3 Met | Chronological holdout, leakage prevented at every stage, val-to-test F1 gap (`@sec:temporal-stability`) | chronological split (`labelling.py`), expanding-window CV + `max(train)<min(val)` assertion (`training.py`), `run_cross_validation.evaluate_cross_dataset` | holdout metrics, `@tbl:transfer` |

The tier machinery behind O1 is confirmed present and tested: `validate_success_tiers`
and `produce_final_summary` in `evaluation.py`, wired into `run_training.py` (which prints
per-model tier and `overall_pass`), and covered by `test_evaluation_significance.py`
(stretch/target/below-minimum classification, `overall_pass` true/false cases, JSON
round-trip asserting `success_tier_achieved`). O2's and O3's evidence functions were
verified in the R6/R27 assessments and persist to `output/evaluation/*_final_summary.json`.

---

## Verdict

**R31: PASS.** The three original objectives (O1–O3, `@tbl:objectives`) are each revisited
individually in a dedicated evaluation section (`@sec:eval-objectives`,
`@tbl:objective-verdicts`), each receives an explicit verdict on the
achieved/partially-achieved/not-achieved scale (all "Met"), and each verdict is tied to
named evidence (`@tbl:perf-default`, `@tbl:baselines`, `@sec:statistical-validation`,
`@sec:complexity-density`, `@sec:temporal-stability`) that is produced by pipeline code
(`validate_success_tiers`, `mcnemar_pairwise_test`, `compute_bootstrap_ci`,
`evaluate_baselines`, the temporal split/CV, and `run_cross_validation`) and persisted to
`output/evaluation/*_final_summary.json`. The Conclusion reaffirms the per-objective
outcome and bounds it with evidence-based limitations, so the evaluation returns to the
objectives rather than merely restating them.

### Minor observations (not blocking)

- The report labels verdicts "Met" rather than the literal words "achieved / partially
  achieved / not achieved." This is the same scale; the discriminating use of "No" and
  "Partial" in the adjacent `@tbl:acceptance-eval` confirms the project applies a graded
  scale rather than passing everything, so the wording does not weaken R31.
- All three objectives are judged "Met" at the *objective* level, while the *operational*
  targets are only partly met. R31 asks that each objective be individually evaluated with
  evidence, which is satisfied; it does not require that every objective be achieved.
