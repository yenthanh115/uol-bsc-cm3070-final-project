# R16 — Feature engineering is documented

**Requirement:** Feature engineering is documented
**Acceptance / validation criterion:** Formula/algorithm, window, transformation and intended
interpretation of important engineered features are described.
**Priority:** MUST

**Verdict: PASS**

The engineered features are documented on all four dimensions the criterion names — formula/
algorithm, window, transformation, and intended interpretation — in both the report and the
code. The report gives a definition table, a per-feature computation table naming the
responsible function, and a code listing for the most involved feature; the code carries a
module-level catalogue and per-function docstrings stating windows, formulae, and edge-case
handling. Together these describe every important engineered feature, satisfying R16.

---

## Evidence from the report (`final-report-v0.0.2.md`)

### 1. Definition table — what each feature is (`@sec:feature-engineering`)

[@tbl:feature-definitions] lists all 11 features with category and a short definition, e.g.
`ticker_post_rate_24h` (Activity, "Same-ticker posts in preceding 24 hours"),
`ticker_post_acceleration` (Activity, "Rate ratio: count in preceding 12h ÷ count in 12h before
that"), `sentiment_score` (Content, "VADER compound sentiment of the post text"),
`word_count_x_hour` and `accel_x_time_since_prev` (Interaction). The caption states all
features use "backward-looking or concurrent information only".

### 2. Per-feature computation table — algorithm, window, transformation, interpretation ([@tbl:feature-detail])

The Implementation section's [@tbl:feature-detail] documents, for every feature, the exact
computation method, the responsible function, the window, and what it captures. Examples:

- **Formula/algorithm + window:** `ticker_post_rate_24h` "counts all other posts mentioning X
  with timestamps in the half-open interval `(t − 24h, t)` … via `np.searchsorted` … The
  self-post is excluded by using `side='left'`."
- **Transformation:** `ticker_post_acceleration` "Splits the backward 24h window into two 12h
  halves … Computes ratio: `count_recent / max(count_older, 1)`", with boundary semantics and
  the divide-by-zero guard described.
- **Intended interpretation:** `time_since_previous` returns hours since the prior same-ticker
  post ("−1 for first occurrence"); `hour_of_day` "captures intraday cyclicality aligned with
  US market hours"; `word_count_x_hour` "encodes the hypothesis that long analytical posts at
  peak trading hours … are stronger surge precursors than either signal alone".

### 3. Algorithm listing for the most involved feature ([@lst:acceleration])

The report reproduces the `ticker_post_acceleration` split-window binary-search algorithm as a
code listing, with a caption explaining the recent/older 12h halves, the ratio's meaning
(>1.0 accelerating, <1.0 decelerating), and the `max(..., 1)` guard.

### 4. Target-side transformations documented too (`@sec:surge-definition`, `@lst:surge-labelling`)

The composite-metric formulae (ΔV, ΔS, z-scores, weighted composite, threshold τ) and the
z-score transformation with train-only μ/σ are given as explicit equations and a code listing,
covering the engineered signals that feed labelling.

### 5. Design-level rationale (`@sec:feature-engineering`, [@tbl:signal-families])

The report ties the four feature categories back to the literature's signal families and
explains the two interaction terms' purpose, so the *why* (interpretation/justification) is
documented alongside the *how*.

## Evidence from the codebase (`src/`)

### 1. Module-level feature catalogue — `features.py`

The module docstring enumerates all 11 features with their windows and transformations:

```text
Base features (9):
  1. sentiment_score — reuse sentiment_polarity from sentiment stage
  2. hour_of_day — extract from created_utc (0–23)
  3. day_of_week — extract from created_utc (0–6, Monday=0)
  4. time_since_previous — hours since last post mentioning same ticker (−1 if first)
  5. ticker_post_rate_24h — reuse backward_count from windowing
  6. ticker_post_acceleration — ratio of 12h/12h backward counts
  ...
Interaction features (2, experiment B2):
  10. word_count_x_hour — word_count × hour_of_day (long posts at peak hours)
  11. accel_x_time_since_prev — ticker_post_acceleration × time_since_previous
```

### 2. Per-function docstrings — formula, window, edge cases

Each helper documents its algorithm precisely, e.g. `_compute_ticker_post_acceleration`:

```python
"""Compute ticker post acceleration using searchsorted.
acceleration = count_in_(t-12h, t] / max(count_in_(t-24h, t-12h], 1)
If denominator is zero ... set value to the numerator count — treating empty
denominator as 1 (R11-AC10)."""
```

and `_compute_time_since_previous` documents the vectorised `np.diff` gap computation and the
`-1` first-occurrence convention. Inline comments in `compute_features` give the boundary
semantics (`side='right'`/`side='left'`) for every windowed feature.

### 3. Windows and transformations centralised — `windowing.py`, `sentiment.py`, `labelling.py`

- `windowing.py` documents the backward `(t − 24h, t)` and forward `(t, t + 24h]` windows and
  the `posting_volume_growth = (forward / max(backward,1)) − 1` transformation.
- `sentiment.py` documents the VADER compound score with title-fallback and the forward-window
  mean/`sentiment_change` transformation.
- `labelling.py` documents the z-score normalisation and weighted composite thresholding.
- `config.py` names the window constant `WINDOW_SECONDS = 24*60*60`, the single source for the
  24h window used across features.

### 4. Report ↔ code agreement

The report's [@tbl:feature-detail] cites the actual function names (`windowing.compute_windowed_counts`,
`features._compute_time_since_previous`, `features._compute_ticker_post_acceleration`,
`sentiment.compute_sentiment`), and the `FEATURE_COLUMNS` list in `features.py` matches the 11
features documented, so the documentation describes the implementation as built.
