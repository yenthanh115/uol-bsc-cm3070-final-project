# X6 — Feature timestamps do not represent real availability

**Severity:** CRITICAL
**Failure mode:** Feature timestamps do not represent real availability (a feature's value
could not genuinely have been known at prediction time `t`, causing subtle temporal leakage
even when the train/test split itself is correct).
**Why dangerous:** Subtle temporal leakage even though the split itself is correct.
**Final validation:** For each feature ask: "Could this value genuinely have been known at
prediction time?"
**Assessed:** 2026-09-05
**Status:** **PASS**

X6 is CRITICAL and differs from X1 (target value in a predictor) and X4 (label-vs-prediction
timing): it asks, per feature, whether the feature's *value* is genuinely available at the
prediction point `t`. This was checked by reading `features.compute_features()` and its helpers
and evaluating each of the 11 feature columns against the availability test. Every feature is
computed from data at or before `t` (backward-looking or a property of the record itself), and
the module hard-asserts chronological order before any backward computation, so no feature
silently uses future information.

---

## Per-feature availability audit (all 11)

| # | Feature | Source / window | Known at `t`? |
|---|---------|-----------------|---------------|
| 1 | `sentiment_score` | VADER compound of the record's **own** title/selftext (its text at creation) | ✔ own content at `t` |
| 2 | `hour_of_day` | `created_utc.dt.hour` — the record's own timestamp | ✔ at `t` |
| 3 | `day_of_week` | `created_utc.dt.dayofweek` — own timestamp | ✔ at `t` |
| 4 | `time_since_previous` | `np.diff` of same-ticker timestamps within a chronologically sorted group → gap to the **immediately preceding** post; `-1` for first occurrence | ✔ prior post only (`< t`) |
| 5 | `ticker_post_rate_24h` | reuses `backward_count` over `(t-24h, t)`, self excluded (`side='left'` at `t` in windowing) | ✔ backward only |
| 6 | `ticker_post_acceleration` | recent half `(t-12h, t)` via `recent_right = searchsorted(times, t, side='left')` (excludes self, strictly `< t`) ÷ older half `(t-24h, t-12h]` | ✔ backward only |
| 7 | `word_count` | token count of own `title + selftext` | ✔ own content at `t` |
| 8 | `title_length` | token count of own `title` | ✔ own content at `t` |
| 9 | `num_tickers_mentioned` | distinct tickers within the **same original post** (`groupby('id')['ticker'].nunique`) | ✔ own content at `t` |
| 10 | `word_count_x_hour` | `word_count × hour_of_day` (product of #7 and #2) | ✔ both at `t` |
| 11 | `accel_x_time_since_prev` | `ticker_post_acceleration × time_since_previous` (product of #6 and #4; `-1` clamped to 0) | ✔ both backward |

Every feature is either a property of the record itself at `t` (1, 2, 3, 7, 8, 9) or derived
from strictly earlier same-ticker posts (4, 5, 6), or a product of such quantities (10, 11).

## Key availability details verified in code

- **Self-exclusion in backward windows.** In `ticker_post_acceleration`, the recent-half right
  boundary is `searchsorted(times, times, side="left")` — the first index where time `>= t` —
  so the record itself is *excluded* and the recent count covers `(t-12h, t)` strictly before
  `t`. Likewise `backward_count` (feeding `ticker_post_rate_24h`) excludes self. So none of the
  activity features "peek" at the current record's own future neighbours.
- **`time_since_previous` looks only backward.** It is the successive time difference within a
  time-sorted ticker group (`np.diff(times)`), assigned to `idx[1:]`; the first occurrence stays
  `-1`. It therefore uses only the preceding post, never the next one.
- **Feature sentiment ≠ target sentiment.** `sentiment_score` reuses `sentiment_polarity`, the
  VADER score of the record's *own* text at `t`. This is distinct from the target's
  `mean_future` sentiment over `(t, t+24h]` (X4). The feature is available at `t`; the
  forward-window mean is never used as a feature.
- **No post-hoc engagement.** `score`/`num_comments` (which accumulate after `t`) are not among
  `FEATURE_COLUMNS` and are asserted absent by `test_features.py`
  (`test_features_exclude_score_and_num_comments`).
- **Chronological-order guard.** `compute_features()` raises if `np.diff(epoch_seconds) < 0`,
  i.e. it refuses to run on unsorted data. This protects the `searchsorted`/`diff` backward
  computations from silently producing leaky values if upstream ordering were broken.

## Unit-test corroboration

`test_features.py` (`TestNoFutureLeakage`) constructs a same-ticker sequence and asserts
`time_since_previous` is backward-only (first record `-1`; later records equal the gap to the
*previous* post, not the next), and asserts post-hoc engagement columns are excluded. These
run before every experiment, giving continuous protection against a refactor introducing a
forward-looking feature.

## Status

**X6: PASS.** Every one of the 11 features represents information genuinely available at the
prediction point `t`: content features (`sentiment_score`, `word_count`, `title_length`,
`num_tickers_mentioned`, `hour_of_day`, `day_of_week`) are properties of the record itself at
creation, and activity features (`time_since_previous`, `ticker_post_rate_24h`,
`ticker_post_acceleration`) are computed strictly from earlier same-ticker posts with the
current record excluded from its own backward window. The two interaction terms are products of
these `≤ t` quantities. Post-hoc engagement is excluded, the feature-side sentiment is the
record's own (not the forward-window target sentiment), and a chronological-order assertion plus
`test_features.py` guard against silent regressions. There is no subtle feature-availability
leakage.

### Minor observations (not blocking)

- `sentiment_score` is available at `t` and thus X6-clean, but it shares the VADER pipeline with
  the target's forward-window sentiment term; that is a feature-importance interpretation caveat
  (X10 / limitations), not an availability problem.
- `num_tickers_mentioned` is computed over the exploded rows of the *same* post `id`. Because all
  those rows share the one post's creation time `t`, the count is fully known at `t`; it does not
  draw on other posts. Not leakage.
