# R24 — Class imbalance is handled analytically

**Requirement:** Class imbalance is handled analytically
**Acceptance / validation criterion:** Accuracy is not used alone; imbalance effects and
relevant mitigation/evaluation choices are explained.
**Priority:** MUST

**Verdict: PASS**

The severe class imbalance (~100:1) is handled analytically on both clauses of the criterion.
Accuracy is explicitly rejected as a standalone metric — AUC-ROC is the primary metric,
reported alongside precision, recall, F1, and PR-AUC — and the report explains the imbalance's
effects (uninformative accuracy, probability compression, precision ceiling) and the concrete
mitigation and evaluation choices made in response (cost-sensitive learning, threshold tuning,
rank-based deployment). These choices are implemented in the code.

---

## Evidence from the report (`final-report-v0.0.2.md`)

### Accuracy is not used alone
- **Model Selection** states plainly: "With surge rates of 1–5%, accuracy is uninformative, a
  naive 'no surge' predictor achieves 95–99%. AUC-ROC measures ranking quality across all
  thresholds. Precision, Recall, F1, and PR-AUC are reported as secondary metrics."
- **Dataset and Target Analysis** repeats it: "a trivial 'never surge' classifier scores 99%
  accuracy, so accuracy is uninformative and ranking metrics are essential."
- **[@tbl:eval-metrics]** lists AUC-ROC (primary), precision, recall, F1 — accuracy is not the
  headline metric; results tables ([@tbl:perf-default], [@tbl:perf-tuned]) report
  AUC/precision/recall/F1 with bootstrap CIs, not accuracy.

### Imbalance effects are explained
- **Dataset and Target Analysis** quantifies the imbalance (WSB 0.97%, 102:1; pennystocks
  0.95%, 105:1) and explains why it makes the problem hard.
- **Model Performance** explains probability compression: "With sub-1% surge rates, probability
  outputs cluster far below 0.5 … This is a calibration problem, not a discrimination failure."
- **[@sec:complexity-density]** links imbalance to XGBoost's probability saturation and zero
  positive predictions at 0.5.
- **[@sec:operational-precision]** and the Limitations ("Class imbalance as deployment
  constraint") explain the precision ceiling: even a perfect ranker faces a precision limit at
  sub-1% prevalence, so no single threshold meets both recall and precision targets.

### Mitigation / evaluation choices are explained
- **Handling class imbalance (Model Selection):** cost-sensitive learning —
  `class_weight='balanced'` for LR and RF, `scale_pos_weight` (neg/pos ratio) for XGBoost — and
  an explicit rejection of SMOTE for temporal data (also in [@tbl:design-alternatives]).
- **Metric choice:** AUC-ROC primary; PR-AUC invoked because "under severe imbalance,
  precision-recall analysis reveals limitations that ROC curves mask" ([@sec:operational-precision],
  Saito & Rehmsmeier [3]); PR-AUC ≈ 0.14 (14× above random) reported.
- **Threshold tuning:** F1-optimised thresholds locked on the validation fold, and a
  precision-floor operating-point concept tied to the ≥0.10 acceptance criterion.
- **Deployment response:** rank-based top-k review recommended precisely because binary
  decisions are unreliable at this base rate ([@sec:operational-precision]).

## Evidence from the codebase (`src/`)

### 1. Cost-sensitive mitigation implemented — `training.py`

- `_make_lr` and `_make_rf` set `class_weight='balanced'`.
- `_make_xgb` sets `scale_pos_weight`, and `_get_xgb_param_grid` builds a
  `{1, ratio/2, ratio}` grid "for class imbalance handling"; the neg/pos `imbalance_ratio` is
  computed from the training partition in `train_all_models`. Matches [@lst:model-factory] /
  [@lst:imbalance-ratio].

### 2. Metric suite is imbalance-appropriate, not accuracy-alone — `evaluation.py`

- Model selection and reporting are driven by **`roc_auc_score`** (grid search optimises mean
  validation AUC; `best_model_by_auc`/`best_auc` summarise runs), with precision, recall, and F1
  computed alongside for every model. `permutation_importance` also uses `scoring="roc_auc"`.
- `find_optimal_threshold` supports a **`precision_floor=0.10`** strategy — the ≥0.10 precision
  acceptance criterion baked into operating-point selection — plus F1-maximisation.
- Bootstrap CIs and McNemar's tests quantify uncertainty and significance under imbalance
  (`evaluation.py`), rather than relying on a point accuracy.

### 3. Evaluation figures reflect imbalance handling — `evaluation_figures.py`

ROC curves and threshold-sensitivity plots are generated (`roc_auc_score`, `roc_curve`), and
the report's confusion matrix and threshold-sensitivity figures visualise the imbalance and the
precision/recall trade-off directly.

### Report ↔ code agreement

The report's stated mitigation (`class_weight='balanced'`, `scale_pos_weight`, SMOTE rejected)
matches `training.py`; the "AUC-ROC primary, precision/recall/F1/PR-AUC secondary" claim matches
the metric computation in `evaluation.py`; the precision-floor criterion matches
`find_optimal_threshold`.
