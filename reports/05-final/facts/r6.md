# R6 — Project objectives are measurable

**Requirement:** Each major objective can be mapped to an implementation output and evaluation result.
**Priority:** MUST
**Assessed:** 2026-09-05
**Verdict:** **PASS**

R6 requires that every major project objective is (a) stated with a measurable success
test, (b) mappable to a concrete implementation output (code that produces the evidence),
and (c) mappable to an actual evaluation result. The report defines three objectives, each
with an explicit success test; all three trace cleanly to code and to reported results.

---

## The objectives and their stated success tests

From the report (§ Aim, Objectives and Contributions, `@tbl:objectives`):

| # | Objective | Success test (report) |
|---|-----------|-----------------------|
| O1 — Predict | Build a model from early-stage discussion features that forecasts surges before they occur | Model clears the target AUC-ROC tier (`@tbl:success-tiers`) on held-out future data |
| O2 — Compare | Establish whether more complex models improve prediction over simpler baselines | Model differences quantified with uncertainty and significance (`@sec:statistical-validation`) |
| O3 — Validate temporally | Establish whether predictions hold on unseen future periods under leakage-free evaluation | No feature/label/statistic draws on future data; results on a chronological holdout |

Each success test is numeric or procedurally checkable (an AUC tier, a significance test,
a leakage-free chronological protocol), so the objectives are measurable in principle. The
rest of this assessment confirms each maps to real code output and a real result.

---

## O1 — Predict: maps to implementation output and result

**Success test is quantified.** The AUC-ROC tiers are hard-coded constants, matching the
report's `@tbl:success-tiers` (Minimum 0.60 / Target 0.70 / Stretch 0.80):

- `src/surge_pipeline/evaluation_models.py`:
  `SUCCESS_TIER_MINIMUM = 0.60`, `SUCCESS_TIER_TARGET = 0.70`, `SUCCESS_TIER_STRETCH = 0.80`.

**Implementation output.**
- `evaluation.validate_success_tiers()` classifies each model's AUC into
  minimum/target/stretch/below_minimum against those constants.
- `evaluation.evaluate_model()` / `evaluate_trained_model()` compute AUC-ROC (plus
  precision, recall, F1, confusion matrix) on the `test` partition.
- `run_training.py` §4 evaluates every model on the held-out test partition
  (`partition == "test"`), §8 runs success-tier validation, and §9/§11 write
  `<prefix>_final_summary.json` and `<prefix>_evaluation_metrics.json`.

**Evaluation result.** Report `@tbl:perf-default` / `@tbl:objective-verdicts`: XGB 0.892 and
RF 0.880 on WSB (stretch), RF 0.753 on pennystocks (target) — i.e. the tier test is applied
and reported. O1 verdict "Met" is grounded in the tier-classification output.

**Mapping:** O1 → `validate_success_tiers` + test-partition metrics (code) → tier results in
`final_summary.json` and `@tbl:perf-default` (result). ✔

---

## O2 — Compare: maps to implementation output and result

**Success test is quantified.** "Differences quantified with uncertainty and significance."

**Implementation output.**
- `evaluation.mcnemar_pairwise_test()` — pairwise McNemar's test with Bonferroni-corrected
  α across model pairs (significance).
- `evaluation.compute_bootstrap_ci()` — 1,000-resample bootstrap 95% CIs for AUC/precision/
  recall/F1 (uncertainty).
- `evaluation.evaluate_baselines()` — random baseline (0.5) and per-feature single-feature
  LR AUCs, plus `improvement_over_best_single_feature` (comparison vs baselines).
- `run_training.py` §5 (McNemar), §6 (baselines), §7 (bootstrap CIs) orchestrate and print/
  save these; results land in `final_summary.json`.

**Evaluation result.** Report `@tbl:mcnemar` (all pairs p < 0.001), `@tbl:perf-default` AUCs
with bracketed 95% CIs, and `@tbl:baselines` (Δ over best single feature). The
complexity-vs-density inversion (`@sec:complexity-density`) interprets the comparison.

**Mapping:** O2 → `mcnemar_pairwise_test` + `compute_bootstrap_ci` + `evaluate_baselines`
(code) → `@tbl:mcnemar`, CI columns, `@tbl:baselines` (result). ✔

---

## O3 — Validate temporally: maps to implementation output and result

**Success test is procedural/checkable.** "No feature, label, or statistic draws on future
data; results reported on a chronological holdout."

**Implementation output.**
- Chronological 80/20 split and train-only z-score stats in `labelling.py`
  (documented in report `@lst:surge-labelling`).
- Expanding-window CV with a hard temporal-ordering assertion
  `max(train_ts) < min(val_ts)` in `training.py` (`@lst:expanding-splits`).
- Per-fold `StandardScaler` fit on training indices only (`@lst:grid-search`).
- Test evaluation restricted to `partition == "test"` in `run_training.py` §4 and
  `evaluation.evaluate_*`.
- Cross-dataset transfer (`run_cross_validation.py`) as an additional generalisation check.
- Leakage guarded by tests: `test_labelling.py` (train-only μ/σ), `test_features.py`
  (backward-only features; `score`/`num_comments` excluded), `test_training.py`
  (chronologically ordered folds).

**Evaluation result.** All headline metrics reported on the chronological holdout
(`@tbl:perf-default`), transfer AUCs in `@tbl:transfer`, and the validation-to-test F1 gap
analysed in `@sec:temporal-stability`. O3 verdict "Met" in `@tbl:objective-verdicts`.

**Mapping:** O3 → chronological split + expanding-window CV + leakage tests (code) →
holdout metrics + transfer + temporal-stability analysis (result). ✔

## Verdict

**R6: PASS.** All three major objectives are stated with measurable success tests, each
maps to concrete implementation output in `/src`
(`evaluation.py`, `evaluation_models.py`, `training.py`, `labelling.py`,
`run_training.py`, `run_cross_validation.py`, and the leakage tests), and each maps to a
reported evaluation result (`@tbl:perf-default`, `@tbl:mcnemar`, `@tbl:baselines`,
`@tbl:transfer`, `@sec:temporal-stability`). The success-tier thresholds in code
(0.60/0.70/0.80) match the report's tier table exactly, so O1's test is verifiable rather
than asserted.

### Minor observations (not blocking)

- The three objectives are project-level research objectives, not the granular per-user
  operational targets. Those operational criteria (`@tbl:acceptance-criteria`) are also
  measurable and separately evaluated (`@tbl:acceptance-eval`), which strengthens R6 but is
  not required by it.
- "Measurable" here is satisfied at the objective level; R6 does not require every objective
  to be *met*, only to be mappable to an output and a result — which holds even where a
  criterion (e.g. recall ≥ 0.50) is not achieved.
