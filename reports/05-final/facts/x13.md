# X13 — Class labels / probability orientation reversed

**Severity:** CRITICAL
**Failure mode:** Class labels or probability orientation reversed (e.g. positive class mapped
to 0, or `P(surge)` actually being `P(no-surge)`), a surprisingly easy implementation error.
**Why dangerous:** Surprisingly easy implementation error that can silently invert results.
**Final validation:** Manually inspect several `y_true`, `y_pred`, `P(surge)` examples.
**Assessed:** 2026-09-05
**Status:** **PASS**

X13 was validated exactly as the checklist prescribes: by manually inspecting concrete
`y_true` / `y_pred` / `P(surge)` examples from the saved prediction-examples artefact, and by
confirming the label encoding and probability-column convention in code. The orientation is
correct throughout — positive class `1` = surge, `predicted_probability` = P(surge), high
probability aligns with `predicted_label = 1` aligns with actual surges. Nothing is inverted.

---

## 1. Label and probability convention in code ✔

- **Positive class = surge = 1.** `labelling.py`: `surge_label = np.where(composite > tau, 1.0, 0.0)`
  — a record is labelled `1` when its composite exceeds the threshold, i.e. `1` = surge, `0` = no
  surge.
- **`P(surge)` = `predict_proba[:, 1]`.** Everywhere probabilities are taken
  (`training.py`, `evaluation.py`, baselines) the code uses `model.predict_proba(...)[:, 1]`.
  With labels `{0, 1}`, sklearn orders `predict_proba` columns by `classes_ = [0, 1]`, so column
  `1` is P(class = 1) = P(surge). Consistent across all call sites.
- **Confusion matrix uses explicit label order.** `confusion_matrix(y_true, y_pred, labels=[0, 1])`
  is used in `evaluation.py`/`evaluation_figures.py`, so TN/FP/FN/TP map to the intended cells,
  and `support_pos = int(y_true.sum())` counts class‑1 (surges) — consistent with `1` = positive.

## 2. Manual inspection of `y_true` / `y_pred` / `P(surge)` examples ✔

From `output/evaluation/prediction_examples_A2_xgboost.json` (XGBoost, tuned threshold **0.85**,
68,923 test records, 668 actual surges), one representative row per confusion cell:

| Cell | `predicted_probability` (P(surge)) | `actual_label` | `predicted_label` | Consistent? |
|------|-----------------------------------|----------------|-------------------|-------------|
| TP | 0.9665 | 1 | 1 | ✔ high P → predict surge → is surge |
| FP | 0.9578 | 0 | 1 | ✔ high P → predict surge → not surge |
| FN | 0.0333 | 1 | 0 | ✔ low P → predict no-surge → is surge |
| TN | 0.0063 | 0 | 0 | ✔ very low P → predict no-surge → not surge |

Across all listed examples the pattern holds without exception:

- **True positives** (5 rows): `actual=1`, `predicted=1`, P ∈ [0.9433, 0.9665] — all ≥ the 0.85
  threshold.
- **False positives** (5 rows): `actual=0`, `predicted=1`, P ∈ [0.9489, 0.9578] — all ≥ 0.85.
- **False negatives** (5 rows): `actual=1`, `predicted=0`, P ∈ [0.0333, 0.0813] — all well below
  0.85.
- **True negatives** (5 rows): `actual=0`, `predicted=0`, P ∈ [0.0063, 0.0070] — all far below
  0.85.

This is the exact signature of **correct** orientation: `predicted_label = 1` iff
`predicted_probability ≥ threshold`, positives carry high P(surge), negatives carry low P(surge),
and the `actual_label` semantics match (`1` really is the surge class). A reversed orientation
would show the opposite — e.g. true surges (TP/FN) clustering at low probabilities, or the
threshold rule pointing the wrong way — which is not observed.

## 3. Internal consistency with reported results ✔

The artefact's `counts` are **TP 157 / FP 565 / FN 511 / TN 67,690**, which match the report's
`@tbl:confusion` for XGBoost at threshold 0.85 exactly, and the derived precision
(157 / (157+565) ≈ 0.217) and recall (157 / (157+511) ≈ 0.235) match `@tbl:perf-tuned`. So the
correctly-oriented examples are the same predictions the report's metrics are computed from — the
orientation used for the headline numbers is the one verified here.

## 4. Behavioural sanity ✔

The examples are also semantically coherent: TN rows are high-volume `DWAC` posts during an
established spike (`ticker_post_rate_24h` ≈ 195–216) that the model correctly does not flag as a
*new* surge onset, while FN rows are cold-start posts with little prior activity — consistent with
the report's error analysis (`@sec:error-analysis`). This behavioural coherence would not arise
under a flipped label/probability mapping.

## Status

**X13: PASS.** Class-label and probability orientation are correct and empirically verified.
The positive class is surge = 1, `predicted_probability` is P(surge) taken from
`predict_proba[:, 1]`, and manual inspection of TP/FP/FN/TN examples in
`prediction_examples_A2_xgboost.json` shows the expected alignment (high P(surge) → predicted
surge; low P(surge) → predicted no-surge) with `actual_label` semantics matching. The confusion
counts reconcile exactly with the report's `@tbl:confusion`/`@tbl:perf-tuned`, so the verified
predictions are the ones behind the reported metrics. There is no reversed-orientation error.

### Minor observations (not blocking)

- The inspected artefact is the A2/XGBoost tuned-threshold set (the reported best operating
  point). A matching `prediction_examples_A1_rf.json` exists for Random Forest; spot-checking it
  would extend the same confirmation to the other headline model, though the shared code path and
  identical `predict_proba[:,1]` convention already make a per-model reversal implausible.
- Several TP/FP examples have strongly negative `sentiment_score` (e.g. −0.97): this reflects that
  the surge target keys on sentiment *change* magnitude, not polarity sign, and is consistent with
  the design — not evidence of any orientation flip.
