# R20 — Model pipeline is reproducible

**Requirement:** Preprocessing, feature selection/transformation, training and prediction
can be executed consistently.
**Priority:** MUST
**Assessed:** 2026-09-05
**Verdict:** **PASS**

R20 concerns whether the *modelling pipeline mechanism* — preprocessing, feature
transformation, training and prediction — can be executed **consistently** (deterministic,
seeded, config-driven, and repeatable run-to-run). This is distinct from R7 (accuracy of
the reported raw-record *counts*) and R38 (whether a clean final run reproduces the
*reported* metrics). The R7 finding does not bear on R20: R7 fails only because the
loader's line-oriented `num_rows` fingerprint inflates the reported raw counts, which is a
reporting/fingerprint artefact — the pipeline itself still executes identically and
produces consistent results on the same input. Every element R20 names is implemented,
seeded, exercised by tests, and empirically reproducible.

---

## 1. Preprocessing is deterministic and consistently executed ✔

- `src/surge_pipeline/loader.py` performs a fixed, ordered transformation: text cleaning
  (`[deleted]`/`[removed]`/null → empty string), dual-regex ticker extraction filtered by a
  fixed 297-term stopword lexicon, timestamp normalisation to `datetime64[ns, UTC]` with a
  hard chronological sort, and `pandas.explode()` into one row per record–ticker pair.
- No randomness is involved; the same input yields the same exploded, sorted frame every
  run. A missing timestamp column raises an explicit error rather than failing silently.
- Verified by `src/tests/test_loader.py` (regex extraction, stopword filtering, explosion
  row counts).

## 2. Feature selection / transformation is deterministic and leakage-isolated ✔

- `src/surge_pipeline/features.py` computes a fixed set of eleven backward-only features
  (`FEATURE_COLUMNS`); the column set is fixed in code, so "feature selection" is stable
  across runs. Windowed counts use `np.searchsorted` on sorted arrays (deterministic).
- Scaling is done with `StandardScaler` **fitted on the training fold only** and applied
  to validation/test, both inside CV (`training._train_single_model`) and for the final
  model (fit on the full training partition, reused at prediction time). This makes the
  transform reproducible and prevents cross-partition leakage.
- Verified by `src/tests/test_features.py` (backward-only contracts; `score`/`num_comments`
  structurally excluded) and `src/tests/test_windowing.py`.

## 3. Training is seeded and consistently executed ✔

- `train_models()` (`src/surge_pipeline/training.py`) runs expanding-window temporal CV
  (`N_FOLDS = 4` → 3 splits) with a hard assertion `max(train_ts) < min(val_ts)`
  (`_verify_temporal_ordering`), grid search per model, then retrains the winning config on
  the full training partition.
- The single `config.random_seed` (default **42**) is injected into every estimator:
  `LogisticRegression(random_state=seed)`, `RandomForestClassifier(random_state=seed)`,
  `XGBClassifier(random_state=seed)` (see `_make_lr` / `_make_rf` / `_make_xgb`). The
  labelling pipeline additionally seeds `random` and `numpy` at entry
  (`pipeline.run_pipeline`).
- Grid definitions are fixed in code (LR 10, RF 36, XGB ≤ 50 configs), so the search space
  is identical across runs.
- Verified by `src/tests/test_training.py` (folds chronologically ordered; expanding-window
  splits respect `max(train) < min(val)`; grid sizes ≤ 50).

## 4. Prediction is consistently executed ✔

- Prediction uses the persisted per-model `StandardScaler` then
  `model.predict` / `model.predict_proba` (`training.predict`, and the test-set block in
  `run_training.py`), with a separate `predict_with_threshold()` applying the
  validation-locked threshold. No re-fitting or randomness occurs at prediction time.
- Trained artefacts (model + scaler + best params + locked threshold + seed + phase) are
  serialised with `joblib` to `output/models/…joblib`, and a `latest_models.json` manifest
  is written, so a saved model can be reloaded and re-scored deterministically.

## 5. Configuration and orchestration make runs repeatable ✔

- `PipelineConfig` (`src/surge_pipeline/config.py`) holds every tuneable parameter, is
  JSON-serialisable (`to_json` / `from_json`), and is saved with each run
  (`*_pipeline_config.json`), so a run is fully specified by config + seed.
- CLI entry points (`run_labeling.py`, `run_training.py`, `run_cross_validation.py`) chain
  the stages without embedding logic, and resolve default input via `latest_outputs.json`.
- `experiment_log.py` appends one JSONL record per run capturing the config, the **git
  commit SHA**, output paths and summary metrics, giving a reproducible audit trail.

## 6. Determinism is empirically demonstrated ✔

**Unit-level.** `src/tests/test_pipeline_integration.py` contains a `TestDeterminism`
class asserting that two `run_pipeline` calls with the same config produce identical
labelled DataFrames (`test_deterministic_labelled_df`) and identical stage counts
(`test_deterministic_stage_counts`). The integration suite passes:

```
19 passed in 1.94s   (pytest src/tests/test_pipeline_integration.py)
```

**Run-level (from `output/experiment_log.jsonl`).** Repeated same-config training runs and
a five-seed sweep on `r/pennystocks` (τ = 1.5, w₁ = w₂ = 0.5) reproduce consistently:

| Run | seed | best model | best AUC-ROC |
|-----|------|------------|--------------|
| 2026-07-19_13-14 | 42   | random_forest | 0.752674925737902 |
| 2026-07-19_13-21 | 123  | xgboost       | 0.7337343652205014 |
| 2026-07-19_13-24 | 456  | xgboost       | 0.7337343652205014 |
| 2026-07-19_13-26 | 789  | random_forest | 0.7425216328720308 |
| 2026-07-19_13-28 | 2024 | random_forest | 0.746152776259972 |

- Seeds 123 and 456 produce a **byte-identical** AUC (0.7337343652205014), confirming the
  code path is deterministic given fixed inputs.
- The five-seed range is **0.7337 – 0.7527**, a **0.019** margin, matching the report's
  Implementation-Status claim of "AUC scores spanning 0.734 to 0.753 (a 0.019 margin)".

## Verdict

**R20: PASS.** All four named pipeline elements — preprocessing, feature
selection/transformation, training, and prediction — are implemented as deterministic,
seeded, config-driven stages that can be executed consistently. Determinism is enforced in
code (single global seed propagated to every estimator, `random`/`numpy` seeded at entry,
train-only scaler fitting, fixed feature set and grids), asserted by an integration test
(`TestDeterminism`, 19/19 passing), and demonstrated empirically in the experiment log
(identical AUC for distinct seeds 123/456; a 0.019 five-seed margin matching the report).
The R7 raw-count discrepancy is a fingerprint/reporting artefact and does not affect the
pipeline's execution consistency, so it does not block R20.

**Note (recorded, not blocking for R20):** the report's phrasing that seed 42 produced
"identical AUC values (0.753)" across 2026-07-13 and 2026-07-19 is exact only to three
decimals — the logged values were 0.753937 (2026-07-13_06-14) and 0.752675
(2026-07-19_13-14). These differ because they ran on different labelled-dataset artefacts
generated on different dates, not from a re-run on the same artefact; run-to-run
determinism on a fixed artefact is what the `TestDeterminism` unit test and the identical
seed-123/456 AUCs confirm. This nuance is relevant to R38 (final-run reproducibility of
reported numbers), not to R20's mechanism-consistency criterion.
