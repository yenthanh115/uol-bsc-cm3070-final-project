# X4 — Label construction contradicts prediction timing

**Severity:** FATAL
**Failure mode:** Label construction contradicts prediction timing (the "target" is actually
knowable at or before the prediction point, turning prediction into detection/description).
**Why dangerous:** Turns "prediction" into detection/description.
**Final validation:** Draw one timeline `observation → prediction point → future target
window`; verify every variable against it.
**Assessed:** 2026-09-05
**Status:** **PASS**

X4 is FATAL and was checked directly against the code. Drawing the single timeline the
checklist asks for and verifying every variable against it: the **label is constructed
entirely from the forward window `(t, t+24h]`** (strictly after the prediction point), while
**every predictor is backward/concurrent (`≤ t`)**. The label therefore describes the future
relative to the observation, so the task is genuine prediction, not detection or description.

---

## The one timeline

For a record–ticker pair observed at time `t`:

```
        backward window                prediction        forward / target window
        [t-24h, t)                     point  t          (t, t+24h]
  ├───────────────────────────┤        │        ├──────────────────────────────┤
  PREDICTORS live here                 │        LABEL is built from here
  (backward_count,                     │        (forward_count, mean_future sentiment)
   time_since_previous,                │
   acceleration, sentiment_score …)    │
```

- **Prediction point** = the record's own timestamp `t` (`created_utc`).
- **Predictors** must be computable from `[…, t]` only.
- **Label** must be computable only from `(t, …]`.

Every variable is verified against this timeline below.

## 1. The label is built from the FUTURE window `(t, t+24h]` ✔

The composite surge target combines two forward-looking quantities, both computed on the
strictly-future window:

**Volume growth** (`windowing.compute_windowed_counts`):

```python
# forward window: (t, t + 24h] — posts strictly AFTER t
forward_left  = np.searchsorted(times, times,                  side="right")  # first time > t
forward_right = np.searchsorted(times, times + _WINDOW_SECONDS, side="right")  # first time > t+24h
group_forward = forward_right - forward_left        # self excluded (side='right' at t)
...
posting_volume_growth = (forward_counts / max(backward_counts,1)) - 1
```

`side="right"` at `t` makes the left edge strictly greater than `t`, so the record itself and
anything at/before `t` are excluded — the count is genuinely future.

**Sentiment change** (`sentiment.compute_sentiment`):

```python
# Forward window: (t, t + 24h] — same logic as windowing.py
forward_left  = np.searchsorted(times, times,                  side="right")
forward_right = np.searchsorted(times, times + _WINDOW_SECONDS, side="right")
... mean_future = window_sums / window_counts        # mean sentiment of FUTURE posts
sentiment_change = np.abs(mean_future - polarities)  # future mean minus current post's sentiment
```

So `mean_future` is the mean VADER score of posts *after* `t`, and the target's sentiment term
is the shift from the current post's sentiment to that future mean.

**Composite label** (`labelling.apply_labelling`):

```python
composite    = (w1 * z_volume) + (w2 * z_sentiment)     # both terms forward-derived
surge_label  = np.where(composite > tau, 1.0, 0.0)
```

Both composite terms derive from the forward window, so `surge_label ∈ {0,1}` encodes what
happens in `(t, t+24h]` — a genuine future target.

## 2. Every predictor lives at or before `t` ✔

The predictors used by the models (`FEATURE_COLUMNS`, 11 features) are all backward-looking or
concurrent, so none reads the target window:

- Backward activity: `ticker_post_rate_24h` reuses `backward_count` over `(t-24h, t)`
  (self excluded via `side='left'` at `t`); `time_since_previous` looks only at the immediately
  preceding same-ticker post; `ticker_post_acceleration` compares the two backward 12h halves.
- Concurrent/content: `sentiment_score` is the **current** post's own VADER score (its own text
  at `t`); `word_count`, `title_length`, `num_tickers_mentioned`, `hour_of_day`, `day_of_week`
  are all properties of the record at `t`.
- Interaction terms are products of the above (still `≤ t`).

Crucially, the **feature** `sentiment_score` uses the post's own text (at `t`), whereas the
**target** uses `mean_future` (after `t`): the two are computed on opposite sides of the
timeline, so the label's construction does not reuse a predictor's timing. (The residual
circularity that current-vs-future sentiment share the VADER pipeline is a *feature-importance
interpretation* caveat the report already flags in the limitations, not a timing contradiction.)

## 3. The prediction point is fixed at `t`, and the split respects it ✔

- The prediction point is each record's own `created_utc`; windows are event-relative, so the
  same `observation → t → (t, t+24h]` structure applies uniformly to every record.
- Records whose forward window cannot be formed (fewer than the minimum forward posts, or the
  window runs past the dataset's final timestamp) are **excluded** from labelling rather than
  guessed — so no label is fabricated from a truncated future (`labelling`/`windowing`
  exclusion, `@sec:surge-definition`).
- The train/test split is chronological (80/20 by timestamp), consistent with the timeline: the
  label's future window is what the model must forecast on genuinely later data.

## 4. Report ↔ code agree on the timeline ✔

The report states exactly this timeline: 24-hour backward `[t-24h, t)` and forward `(t, t+24h]`
windows (`@sec:data-representation`, `@sec:surge-definition`), predictors "derived exclusively
from information available at or before observation timestamp `t`" (`@sec:feature-engineering`),
and post-hoc engagement excluded because it accumulates after `t`. The code implements this
precisely, so the documented prediction framing matches the constructed label.

## Status

**X4: PASS.** Label construction does not contradict prediction timing. Drawing the single
timeline `observation → prediction point t → future target window (t, t+24h]`, the surge label
is built exclusively from the strictly-future window — forward post counts (`windowing.py`) and
forward-window mean sentiment (`sentiment.py`), combined and thresholded in `labelling.py` —
while every predictor is computed from the record at `t` or its backward window. The current
post's sentiment (a feature) and the future-window mean sentiment (part of the target) sit on
opposite sides of `t`. Records whose forward window cannot be formed are excluded rather than
labelled from a truncated future. The task is therefore genuine 24-hour-ahead prediction, not
detection or description, and the code matches the timeline the report documents.

### Minor observations (not blocking)

- `sentiment_score` (feature, at `t`) and the target's `sentiment_change` (uses forward-window
  mean) share the VADER pipeline. This is a *timing-clean* setup — opposite sides of `t` — but
  it does introduce a structural correlation that can inflate sentiment's apparent feature
  importance; the report already discloses this in the limitations. It is an interpretation
  caveat (relevant to X10), not an X4 timing violation.
- X4 concerns label-vs-prediction timing specifically. Related leakage vectors — feature
  timestamp availability (X1/X6) and same-episode overlap across the split (X3) — are separate
  checklist items and out of scope here.
