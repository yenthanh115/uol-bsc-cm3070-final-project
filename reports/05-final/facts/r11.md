# R11 — No target leakage

**Requirement:** Every predictive feature can be calculated using only information available within the defined observation window.
**Priority:** CRITICAL
**Assessed:** 2026-09-05
**Verdict:** **PASS**

R11 (CRITICAL) requires that every one of the model's predictive features is computable
from information at or before the record's observation time *t* — nothing may draw on the
forward window or on post-hoc quantities. The observation window is defined in the report as
backward `[t-24h, t)` / creation-time; the forward window `(t, t+24h]` belongs to the target,
not the features. Evidence below verifies this feature-by-feature in code, confirms post-hoc
engagement is structurally excluded, and shows the property is guarded by assertions and
enforced by unit tests.

---

## The feature set under review

`src/surge_pipeline/features.py` defines exactly the 11 predictive features (`FEATURE_COLUMNS`):
`sentiment_score`, `hour_of_day`, `day_of_week`, `time_since_previous`,
`ticker_post_rate_24h`, `ticker_post_acceleration`, `word_count`, `title_length`,
`num_tickers_mentioned`, `word_count_x_hour`, `accel_x_time_since_prev`.
These match the report's `@tbl:feature-definitions` / `@tbl:feature-detail`.

---

## Feature-by-feature admissibility (each ≤ t)

| # | Feature | Source of information | Backward/creation-time only? |
|---|---------|-----------------------|------------------------------|
| 1 | `sentiment_score` | `sentiment_polarity` = VADER on the record's own title/selftext at creation | Creation-time ✔ |
| 2 | `hour_of_day` | `created_utc.dt.hour` | Creation-time ✔ |
| 3 | `day_of_week` | `created_utc.dt.dayofweek` | Creation-time ✔ |
| 4 | `time_since_previous` | Gap to the immediately *preceding* same-ticker post (`np.diff` within chronologically sorted group); −1 if first | Backward-only ✔ |
| 5 | `ticker_post_rate_24h` | Reuses `backward_count` from windowing = posts in `(t-24h, t)` | Backward-only ✔ |
| 6 | `ticker_post_acceleration` | Ratio of counts in `(t-12h, t]` vs `(t-24h, t-12h]` via `searchsorted` | Backward-only ✔ |
| 7 | `word_count` | Tokens in the record's own `title + selftext` | Creation-time ✔ |
| 8 | `title_length` | Tokens in the record's own `title` | Creation-time ✔ |
| 9 | `num_tickers_mentioned` | Distinct tickers within the *same* post (`groupby('id')`) | Creation-time ✔ |
| 10 | `word_count_x_hour` | Product of features 7 and 2 | Derived from backward/creation-time ✔ |
| 11 | `accel_x_time_since_prev` | Product of features 6 and 4 | Derived from backward-only ✔ |

Every feature is a function only of the record's own creation-time content or of strictly
prior same-ticker posts. No feature reads the forward window `(t, t+24h]`.

---

## The backward window genuinely excludes self and future

`windowing.compute_windowed_counts()` computes `backward_count` (the basis of features 5, 6)
with vectorised binary search on the chronologically sorted per-ticker timestamps:

```python
# backward window: (t - 24h, t) — strictly before t, within 24h
backward_left  = np.searchsorted(times, times - _WINDOW_SECONDS, side="right")
backward_right = np.searchsorted(times, times, side="left")   # side='left' at t excludes self
group_backward = backward_right - backward_left
```

Using `side="left"` at the right boundary excludes the record itself, and the left boundary
is `t-24h`, so the count covers only `(t-24h, t)`. `forward_count` is computed separately and
is used **only** for the target metric, never added to `FEATURE_COLUMNS`.
`ticker_post_acceleration` uses the same `side` semantics to keep both 12h half-windows strictly
at or before *t*.

---

## Post-hoc engagement is structurally excluded

Reddit `score` and `num_comments` accumulate *after* posting and would leak the outcome. They
are deliberately kept out of the feature set:

- `features.py` docstring states engagement metrics "(score, num_comments) are explicitly
  excluded (R11-AC9, R12-AC3)".
- `FEATURE_COLUMNS` contains neither field, so `get_feature_matrix()` cannot surface them.
- Report `@tbl:signal-families` classifies post-hoc engagement as "Strong but unusable …
  Excluded: future information", and `@tbl:design-alternatives` records the same exclusion as a
  no-leakage decision.

---

## Guardrails that keep features leakage-free

**Chronological-order assertion.** `compute_features()` (and `compute_windowed_counts()`)
convert `created_utc` to epoch seconds and fail loudly if any record is out of order:

```python
if np.any(np.diff(_epoch_check) < 0):
    raise ValueError("Input DataFrame must be sorted chronologically ... out of temporal order.")
```

This matters because the backward-only features rely on group ordering; unsorted input could
otherwise let a later post influence an earlier one. Making it a crash rather than silent
corruption directly protects the R11 invariant.

**First-occurrence handling.** `time_since_previous` returns −1 for a ticker's first post (no
prior history invented), and `accel_x_time_since_prev` clamps that −1 to 0 to avoid a spurious
product — neither fabricates backward information.

## Tests enforce the R11 contract

`src/tests/test_features.py`, class `TestNoFutureLeakage`, verifies leakage-freedom directly:

- `test_features_exclude_score_and_num_comments` — asserts `score` and `num_comments` are
  absent from both `FEATURE_COLUMNS` and the produced feature matrix. The fixture
  **deliberately includes** `score`/`num_comments` columns in the input, proving they are
  dropped rather than merely absent.
- `test_time_since_previous_is_backward_only` — with AAPL posts at t=0/6/12h, asserts the
  third record reports 6h since the *previous* post (not 12h since the first), i.e. it looks
  backward one step only, and the first occurrence is −1.
- `test_temporal_features_use_creation_time_only` — `hour_of_day`/`day_of_week` match
  `created_utc`.
- `test_ticker_post_rate_uses_backward_count` — feature 5 equals the backward-only count.
- `test_sentiment_score_uses_observation_time_polarity` — sentiment feature equals the
  creation-time polarity.

`test_windowing.py` separately verifies backward/forward counts against hand-computed values
and the boundary inclusion/exclusion semantics. The report notes these run automatically before
every experiment (`@lst:feature-contract`, Testing Strategy).

## Report ↔ code consistency

The report's leakage claims match the code exactly:
- "All eleven features … derived exclusively from information available at or before
  observation timestamp *t*" (§Feature Engineering) ↔ `features.py` construction above.
- Post-hoc engagement excluded (`@tbl:signal-families`, `@tbl:design-alternatives`) ↔
  `FEATURE_COLUMNS` and the exclusion test.
- Backward `[t-24h, t)` / forward `(t, t+24h]` separation (§Surge Definition) ↔ windowing
  `side` semantics.

Note: the separate concern of *label*/normalisation leakage (train-only z-scores) is covered by
R12 and `test_labelling.py`; R11 as scoped here concerns *feature* admissibility, which holds.

---

## Verdict

**R11: PASS.** Every predictive feature is computable from information at or before the
record's observation time: creation-time content (sentiment, word/title counts, hour/day,
same-post ticker count) or strictly prior same-ticker activity (backward count, acceleration,
time-since-previous), with the two interaction terms derived from those. The backward window
excludes self and the future by construction, post-hoc engagement is structurally excluded,
a chronological-order assertion prevents silent leakage, and dedicated unit tests enforce the
contract. Report and code agree.

### Minor observations (not blocking)

- `sentiment_score` uses the record's *current* sentiment, which is admissible under R11;
  a separate, acknowledged *circularity* (current sentiment vs the target's forward sentiment
  shift) is documented in the report's limitations and is not feature leakage.
- Feature correctness relies on the loader supplying globally chronological input; this is
  guaranteed by the loader and re-asserted in both `features.py` and `windowing.py`.
