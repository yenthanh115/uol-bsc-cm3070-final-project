# X9 — Duplicate or near-duplicate observations

**Severity: CRITICAL**
**Failure mode:** Duplicate or near-duplicate observations inflate apparent generalisation.
**Final validation:** Check duplicates before splitting and temporal/window overlap where relevant.

**Verdict: PASS** (within-post duplicates removed by construction; duplicates assessed in EDA before dataset selection; source is submission-ID-keyed; the chronological per-row split cannot place the same row on both sides — with one documented rigour caveat)

## Within-post duplicate tickers are removed by construction (code)

`loader.extract_tickers()` accumulates matches into a `set` and returns `sorted(tickers)`:

```
tickers: set[str] = set()
... tickers.add(ticker) ...   # dollar-sign + uppercase patterns
return sorted(tickers)
```

So a post mentioning the same ticker several times (e.g. `$AMC ... AMC ... $AMC`) yields exactly **one** `AMC` entry. After `df.explode("tickers")`, each exploded row is a distinct `(id, ticker)` pair, and empty tickers are dropped (`df[df["tickers"].str.len() > 0]`). `features._compute_num_tickers_mentioned` then counts *distinct* tickers per `id`. There are therefore no duplicate record–ticker rows generated by extraction/explosion.

## Row-level (duplicate submissions) — checked, and structurally absent

- The loader does not call `drop_duplicates`; the report's Data Loading Step 1 justifies this: "Each raw row maps to a unique Reddit submission ID, so no deduplication is needed." Reddit submission exports are keyed by a unique submission `id`, so identical submissions do not recur.
- Duplicates were **assessed before committing to the datasets**: the EDA deep-assessment notebook (`03_deep_assessment.ipynb`) "measures data quality (duplicates, high-risk columns)" as part of the viability gate (report `@sec:eda-tooling`, `@tbl:eda-deep`). This satisfies the "check duplicates before splitting" validation — the check informed dataset selection, before any train/test split existed.

## Near-duplicate / temporal-window overlap

The only inter-row correlation is the inherent temporal-window overlap: backward (`(t−24h, t)`) and forward (`(t, t+24h]`) counts of nearby records share neighbouring posts. As established in x3.md, this does not duplicate rows across the split:
- The split is a single chronological cut by each row's own timestamp; the **same physical row cannot appear on both sides**.
- Backward-window features use only past posts (available at scoring time); forward-window quantities feed the target only, never features.
- Records whose forward window is too sparse or runs past the dataset boundary are excluded as unlabellable.

So window overlap is a designed property, not near-duplicate contamination that would inflate held-out performance.

## Documented caveat (minor rigour gap, not a defect)

The loader **assumes** source submission-`id` uniqueness rather than **enforcing** it programmatically at full-run scale: there is no `drop_duplicates`/uniqueness assertion on `id`, and the EDA duplicate check ran on a sampled subset (up to 100k rows), not the complete dataset. No actual duplicates are evidenced, and the design structurally prevents the same row crossing the split, so this does not inflate generalisation — but a full-run uniqueness assertion would make the guarantee airtight. Recorded here for completeness; it does not change the verdict.
