# R15 — Additional engagement/content features are justified

**Requirement:** Any included feature has a rationale connected to trend emergence rather than being included merely because it exists.
**Priority:** SHOULD
**Assessed:** 2026-09-05
**Verdict:** **PASS**

R15 asks whether the *additional* features beyond the core temporal/volume signals — the
content features, the two interaction terms, and any engagement fields — are each justified by
a rationale tied to surge emergence, not included gratuitously. The strongest evidence for R15
is twofold: (1) every content/interaction feature carries an explicit surge-linked rationale in
both the report and the code, and (2) the obvious "because it exists" candidates — post-hoc
engagement fields (`score`, `num_comments`) — are deliberately **excluded**, which is exactly
the discipline R15 is testing for.

---

## Scope: which features R15 covers

The 11 features (`features.FEATURE_COLUMNS`, report `@tbl:feature-definitions`) fall into four
categories. R13 covers the temporal/activity signals; R15 concerns the **content** features, the
**interaction** terms, and the treatment of **engagement** fields:

- Content: `sentiment_score`, `word_count`, `title_length`, `num_tickers_mentioned`
- Interaction: `word_count_x_hour`, `accel_x_time_since_prev`
- Engagement (Reddit `score`, `num_comments`): **excluded**

Each is examined below for a trend-emergence rationale.

---

## Content features — each has a surge-linked rationale

| Feature | Rationale connected to surge emergence | Source |
|---------|----------------------------------------|--------|
| `sentiment_score` | Sentiment *change* can be a leading indicator of activity surges; a rising emotional charge may precede a volume spike (motivates the composite target too). Literature-grounded (`@tbl:signal-families`, Bollen et al. [12]) | Report §Sentiment as a Predictive Signal; `features.py` feature 4 |
| `word_count` | "Measures post effort/depth as a proxy for informational content" — long analytical "due diligence" posts precede surges (borne out on WSB where `word_count` alone reaches AUC 0.805) | `features.py` feature 5; report `@tbl:feature-detail`, `@sec:cross-community` |
| `title_length` | "Captures headline effort independently of body length" — content-metadata signal supported by Bandari et al. [10] | `features.py` feature 6; report `@tbl:signal-families` |
| `num_tickers_mentioned` | "Captures whether a post is ticker-specific or broad market commentary" — focused single-ticker posts differ from scattershot market chatter in surge relevance | `features.py` feature 7; report `@tbl:feature-detail` |

The report ties the content category explicitly to the literature's "Content metadata" signal
family ("Source, category, named entities predict popularity pre-engagement [10]"), marked
"Partially included (word/title counts, ticker counts)" in `@tbl:signal-families` — i.e. the
inclusion is a deliberate, evidence-backed choice, not incidental.

## Interaction features — hypothesis-driven, not gratuitous

Both interaction terms are introduced with an explicit hypothesis about surge precursors, and
their value is tested rather than assumed:

- `word_count_x_hour`: "Encodes the hypothesis that long analytical posts at peak trading hours
  … are stronger surge precursors than either signal alone" (`features.py` feature 10; report
  `@tbl:feature-detail`).
- `accel_x_time_since_prev`: "Captures the pattern of sudden acceleration after prolonged
  silence — a ticker dormant for many hours that suddenly attracts rapid posting"
  (`features.py` feature 11).

The report states their empirical value "is assessed by ablation in the evaluation"
(§Feature Engineering) and reports the result: "An ablation study confirmed a consistent +1.4pp
AUC lift from including these terms" (§Feature Engineering (Implementation)). So the additional
features are not only justified by rationale but their contribution is quantified — stronger than
R15 (SHOULD) requires.

## Engagement fields — excluded, the decisive R15 evidence

The features most at risk of being "included merely because they exist" are the engagement
fields present in the archive. The project deliberately excludes them, with a documented reason:

- `features.py` docstring: "Engagement metrics (score, num_comments) are explicitly excluded
  (R11-AC9, R12-AC3)"; neither appears in `FEATURE_COLUMNS`.
- Report §Data Representation: engagement fields "are deliberately *not* aggregated into
  features … their values are post-hoc and would leak future information, so they inform only
  dataset selection, never the model."
- `@tbl:signal-families` classifies post-hoc engagement as "Strong but unusable … Excluded:
  future information", and `@tbl:design-alternatives` records the same as a rejected alternative.

This demonstrates the project applies the R15 discipline in the hardest case: a readily
available, individually predictive signal is left out because it lacks an *admissible* rationale
(it would leak), rather than being included for its own sake.

## Each feature traces to a supported signal family

The report's `@tbl:signal-families` maps every included category to prior-work evidence and an
admissibility judgement (volume/activity, growth/acceleration, content metadata, sentiment all
"Included"; network structure and post-hoc engagement "Excluded"). The feature set is therefore
constructed top-down from justified signal families, and `@tbl:feature-detail` gives a
per-feature "what it captures" column — no feature lacks a stated purpose.

---

## Verdict

**R15: PASS.** Every additional content feature (`sentiment_score`, `word_count`,
`title_length`, `num_tickers_mentioned`) and both interaction terms carry an explicit
surge-emergence rationale in the report (`@tbl:signal-families`, `@tbl:feature-detail`,
§Feature Engineering) and in the `features.py` docstrings/comments, and the interaction terms'
contribution is additionally quantified by ablation (+1.4pp AUC). Decisively for R15, the
post-hoc engagement fields that could have been added "because they exist" are explicitly
excluded with a documented leakage rationale. No feature is present without a stated,
emergence-connected justification.

### Minor observations (not blocking)

- `title_length` is described in `@tbl:feature-definitions` as "Character count of title" but is
  implemented as a whitespace token count (`features.py` feature 6, `@tbl:feature-detail`). This
  is a wording inconsistency in one summary table, not a justification gap, and does not affect
  R15 (it is an R39 report-vs-code detail).
- R15 is a SHOULD; the project exceeds it by quantifying the interaction terms' contribution
  rather than merely asserting a rationale.
