# R3 — Prediction horizon is explicit

**Requirement:** Prediction horizon is explicit
**Acceptance / validation criterion:** Observation window and future target window are clearly separated.
**Priority:** MUST
**Assessed:** 2026-09-05
**Verdict: PASS**

The observation (backward-looking) window and the future target (forward-looking) window
are explicitly defined, fixed at a single 24-hour horizon, and kept strictly disjoint in
both the report and the code. The two windows are constructed from the same reference
instant `t` but never overlap: the backward window is the half-open interval `(t − 24h, t)`
and the forward window is `(t, t + 24h]`, with the record's own timestamp `t` excluded from
both. This separation is documented in the report, implemented consistently across the
windowing, sentiment, and labelling stages, and locked in by unit tests on the exact
boundary conditions.

---

## Evidence from the report (`final-report-v0.0.2.md`)

1. **Horizon stated up front.** The abstract and introduction state the target is whether
   discussion will surge "during the following 24 hours" / over "a 24-hour horizon", using
   "only information available when each post is observed" — i.e. an explicit forward target
   window and a backward-only observation window.

2. **Windows separated by design (Design Goal G2).** [@sec:requirements] lists the
   most important design goal as *"No future information … no feature, label, or statistic
   may draw on data later than the record being scored."* This is the explicit statement
   that observation-time inputs and the future target are separated.

3. **Surge definition fixes both windows (`@sec:surge-definition`).** Step 1 of the surge
   definition counts posts "within a backward window `[t − 24h, t)` and a forward window
   `(t, t + 24h]`." Volume growth `ΔV = C_fwd / max(C_bwd,1) − 1` is built from the two
   disjoint counts, so the observation window (`C_bwd`) and the future target window
   (`C_fwd`) are explicitly distinct quantities.

4. **Horizon choice justified.** The *Observation window* paragraph explains why 24h was
   chosen: "A 24-hour window aligns with daily trading cycles. Shorter windows (6h) yield
   sparse per-ticker counts … longer windows (72h) blur surge onset." The horizon is an
   explicit, reasoned parameter, not an implicit default.

5. **Data representation is event-centred (`@sec:data-representation`).** "Windows are
   measured relative to each record's own observation time (`[t−24h, t)` backward,
   `(t, t+24h]` forward), so the representation is event-centred, not grid-centred."

6. **Pipeline architecture ([@tbl:pipeline-stages]).** Stage 2 "Temporal Windowing" is
   described as computing "per-ticker forward and backward 24-hour posting counts",
   confirming both windows are first-class, separated pipeline artefacts.

7. **Feature/target split (`@sec:feature-engineering`).** All 11 features "satisfy a strict
   backward-looking constraint: each is derived exclusively from information available at or
   before observation timestamp `t`", whereas the target is defined over the forward window
   — the two windows feed different sides of the model.

## Evidence from the codebase (`src/`)

### 1. Single, explicit horizon constant — `surge_pipeline/config.py`

The 24-hour horizon is defined once as a named constant and reused everywhere, so the
observation and target windows share one explicit horizon:

```python
#: Temporal window size in seconds (24 hours).
#: Used by windowing (forward/backward counts) and sentiment (forward mean).
WINDOW_SECONDS: int = 24 * 60 * 60
```

### 2. Backward vs forward windows constructed disjointly — `surge_pipeline/windowing.py`

`compute_windowed_counts()` documents and implements the two windows as clearly separated
half-open intervals around `t`, each excluding the record itself:

```python
#   - backward_count: number of OTHER posts mentioning the same ticker
#     in the prior 24h window, i.e. timestamps in (t - 24h, t) exclusive of self.
#   - forward_count: number of posts mentioning the same ticker in the
#     forward 24h window, i.e. timestamps in (t, t + 24h] exclusive of self.
```

The boundaries are computed with `np.searchsorted` so the intervals cannot overlap at `t`:

```python
# backward window: (t - 24h, t)
backward_left  = np.searchsorted(times, times - _WINDOW_SECONDS, side="right")
backward_right = np.searchsorted(times, times,                   side="left")   # excludes self at t
group_backward = backward_right - backward_left

# forward window: (t, t + 24h]
forward_left   = np.searchsorted(times, times,                   side="right")  # excludes self at t
forward_right  = np.searchsorted(times, times + _WINDOW_SECONDS, side="right")
group_forward  = forward_right - forward_left
```

The `side='left'` at `t` for the backward window and `side='right'` at `t` for the forward
window guarantee the record's own timestamp belongs to neither window, keeping the
observation and target windows strictly separated.

### 3. Target uses the forward window only — `surge_pipeline/windowing.py` + `labelling.py`

The forward-growth surge metric derives the target from the forward count relative to the
backward count:

```python
# growth = (forward / max(backward, 1)) - 1
denominator = np.maximum(backward_counts, 1)
posting_volume_growth = (forward_counts / denominator) - 1.0
```

`labelling.py` then thresholds a composite of the (forward-derived) volume growth and the
(forward-derived) sentiment change into the binary surge label — so the label is a function
of the future target window, distinct from the backward observation window used for features.

### 4. Sentiment target also uses the forward window — `surge_pipeline/sentiment.py`

The future-sentiment component of the target reuses the same forward window `(t, t + 24h]`,
reinforcing the separation:

```python
# Forward window: (t, t + 24h] — same logic as windowing.py
forward_left  = np.searchsorted(times, times,                   side="right")
forward_right = np.searchsorted(times, times + _WINDOW_SECONDS, side="right")
...
sentiment_change = np.abs(mean_future - polarities)   # future window vs current record
```

### 5. Boundary separation is locked in by tests — `src/tests/test_windowing.py`

Unit tests assert the exact horizon and the self-exclusion that keeps the windows disjoint:

- `test_record_at_exact_24h_boundary_excluded` — a record exactly 24h away is **not** in
  the window (half-open interval respected).
- `test_record_just_inside_24h_window` — a record at 23h59m **is** in the window.
- `test_self_exclusion` — a record never counts itself in either the forward or backward
  window, so `t` is excluded from both.
- `test_two_records_within_24h` — confirms forward/backward counts are attributed to the
  correct side of `t`.

These tests fix the horizon at exactly 24h and prevent the observation and target windows
from ever overlapping at the boundary instant.
